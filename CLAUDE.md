# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Leben in Gemeinschaft" (ligem, homepage: ligem.de) is a free, common-good-oriented (gemeinwohlorientiert) international platform for all forms of communal living (WGs, Ökodörfer, Co-Housing, Mehrgenerationenhäuser, etc. — not limited to classic WGs). It serves four audiences at once: (1) housing communities presenting themselves / looking for new members, (2) common-good organizations working on communal-living topics, (3) people just informing themselves about communal living (regardless of search intent), (4) organizations/communities posting events, info sessions, or visiting days to a shared calendar. Deliberately **not** styled as spiritual/esoteric, even though a large part of the target audience personally is — tone and design stay neutral/grounded (see the `warm-community-design` skill under `.claude/skills/`).

Key product decisions (from the founder's requirements questionnaire, kept in memory for full detail):
- No automated matching — users only search/filter themselves.
- Listing taxonomy (room, whole unit, project founding, temporary stays, ...) is a freely extensible DB table, not hardcoded; a listing can belong to multiple categories.
- Required fields per listing are deliberately minimal (project name + owner); the long list of possible filters (location, lifestyle, values, decision model, ecology, ...) is explicitly a later expansion, not MVP scope.
- Guest access without login, moderation/approval before publishing, contact details revealed only after the listing owner approves.
- Multi-language content is planned (start: German + English).

Note: the founder's questionnaire originally listed Laravel as a tech preference, but the user has confirmed (2026-07-27) that the project stays on the existing Next.js/React/TypeScript stack below — no migration planned.

The Next.js app has a real domain data model (Prisma schema + migration applied) and a first vertical slice of UI: registration/login, submitting a listing, browsing published listings, and contacting a listing owner (see Pages below).

## Architecture

- Monorepo layout: the Next.js app lives in `apps/web`; the repo root only holds Docker/infra config. There is a root `pnpm-workspace.yaml`-style setup but currently a single app package.
- `docker-compose.yml` at the repo root defines the full dev stack:
  - `postgres` — PostGIS-enabled Postgres (user `c1u3`, db `c1db3` — the actual initialized credentials in the `postgres_data` volume; `DATABASE_URL` must match these, not a nicer-looking placeholder)
  - `valkey` — Redis-compatible cache/queue store
  - `meilisearch` — search engine (likely for searching WGs/orgs/listings)
  - `minio` — S3-compatible object storage (photos/videos/documents on listings)
  - `web` — runs the Next.js app itself via `pnpm dev` inside a `node:22-bookworm` container, with `DATABASE_URL`, `REDIS_URL`, `MEILISEARCH_HOST`/`MEILISEARCH_KEY`, `S3_ENDPOINT`/`S3_ACCESS_KEY`/`S3_SECRET_KEY`, `AUTH_SECRET`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, `ANTHROPIC_API_KEY`, `NEXT_PUBLIC_MAPTILER_KEY` wired in as env vars
- Secrets/config for the compose stack come from a root `.env` (gitignored): `POSTGRES_PASSWORD`, `MEILI_MASTER_KEY`, `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`, `AUTH_SECRET`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (Google OAuth is optional — the provider is only registered in `src/lib/auth.ts` when both are set), `ANTHROPIC_API_KEY` (optional — gates the "KI-Import" button on listing forms, see "Homepage-Feld & KI-Import" below), `NEXT_PUBLIC_MAPTILER_KEY` (optional but strongly recommended — see "Kartenkacheln" below for why raw OpenStreetMap tiles aren't reliable for this app to depend on directly).
- `apps/web` is a standard Next.js App Router project (TypeScript, React 19, Tailwind CSS v4, ESLint 9 flat config). Source lives under `apps/web/src/app`. Path alias `@/*` maps to `apps/web/src/*`.
- **Running commands inside the container vs. on the host is not interchangeable here.** `node_modules` was first installed by the `web` container (pnpm store path `/workspace/.pnpm-store/v11`); running `pnpm` from the host fails with `ERR_PNPM_UNEXPECTED_STORE` because the bind-mounted path resolves differently. Run `pnpm`/`prisma` commands via `docker compose exec web sh -c "cd /workspace/apps/web && <cmd>"` unless you've set up a separate host-side store.

## Data model (Prisma)

- Schema: `apps/web/prisma/schema.prisma`. Config (datasource URL, migrations path, seed command) lives in `apps/web/prisma.config.ts`, **not** in the schema file — this is Prisma 7, which moved connection handling to driver adapters (see below) and dropped `datasource.url` from `schema.prisma`.
- Client generation: `generator client { provider = "prisma-client" }` generates plain TypeScript (not the old `prisma-client-js`) into `apps/web/src/generated/prisma/` (gitignored, regenerated via `prisma generate`, wired into `postinstall`). Import from `@/generated/prisma/client` (or `../src/generated/prisma/client` from `prisma/seed.ts`) — there is no barrel `index`.
- Prisma 7 requires an explicit driver adapter at runtime: `apps/web/src/lib/prisma.ts` builds a `PrismaClient` with `@prisma/adapter-pg` (`pg` driver), not a bare `new PrismaClient()`. Reuse that shared instance instead of instantiating a new client per file.
- PostGIS: enabled via `previewFeatures = ["postgresqlExtensions"]` and `extensions = [postgis]` on the datasource. Location columns (`Listing.location`, `Event.location`) are typed `Unsupported("geometry(Point, 4326)")` — Prisma Client can't read/write them directly, use `$queryRaw`/`$executeRaw` for anything geo (distance search, map clustering). Both `Listing` and `Event` keep plain `latitude`/`longitude` Float columns in sync with `location`: `src/lib/geo.ts` (`setListingLocation`/`setEventLocation`) pushes lat/lng into `location` via `$executeRaw` `ST_SetSRID(ST_MakePoint(lng, lat), 4326)` after every create/update; radius search (`/termine`) runs `$queryRaw` with `ST_DWithin(location::geography, ..., radiusMeters)` to get matching IDs, then a normal `findMany({ where: { id: { in } } })` for the rest.
- Geocoding: `src/app/api/geocode/route.ts` proxies OpenStreetMap's Nominatim (free, no API key, but rate-limited and requires an identifying `User-Agent` — already set) for both free-text place search (`?q=`) and structured lookups (`?postalcode=&city=&street=&country=`). All actual geocoding happens **client-side** — `src/components/address-fields.tsx` (Land/Bundesland auto-filled from PLZ, full-address geocode with a fallback to city-only if the street doesn't resolve or the result's postcode disagrees with the input, plus a Leaflet map to override by click or browser geolocation) and `src/components/location-radius-picker.tsx` (place search + radius slider, used by both `/termine` and `/projekte`'s search) both just populate hidden `latitude`/`longitude` form inputs — the server actions never geocode anything themselves, they only persist whatever coordinates arrived. `address-fields.tsx`'s map also uses `getLeafletWithCluster()` (see below) purely to get the same `gestureHandling: true`/`scrollWheelZoom: false` behavior as the Umkreissuche map (scrolling the page over it shouldn't hijack the scroll into a zoom) — it doesn't need clustering itself, just the shared plugin-registration singleton that helper already provides.
- `location-radius-picker.tsx` also draws an `L.circle` overlay sized to the selected radius (radius step in km × 1000) around the current point, and calls `map.fitBounds(circle.getBounds(), ...)` whenever the marker moves or the radius slider changes, so the visible map always matches the active search radius; picking "Alle" (the last slider step, radius `null`) removes the circle without forcing a specific zoom. The search-origin marker is a custom pin (`L.divIcon` with an inline SVG teardrop, no external image asset) rather than the plain `circleMarker` dot used for results, so "where I'm searching from" is visually distinct from "what was found". The map is created with `scrollWheelZoom: false` (scrolling the page over an embedded map shouldn't hijack the scroll into a zoom), is deliberately compact (`h-56`/`h-40`), and has a small "✕" button (top-right, overlaid) that hides it and swaps in a "👁️ Karte einblenden" button — hiding toggles a Tailwind `hidden` class on the *same* container div rather than conditionally rendering it, since removing/re-adding the div from the DOM would detach it from the already-created Leaflet map instance (the map is only ever constructed once, in a mount effect with an empty dependency array); un-hiding calls `map.invalidateSize()` on the next frame, since Leaflet doesn't notice its container resizing while `display: none`. The radius `<input type="range">` uses a `.ligem-radius-slider` class (defined in `globals.css`, since Tailwind has no utilities for slider thumbs) for a much larger (32px) thumb than the browser default — needed for reliable touch dragging on small screens. Within the `Umkreissuche` fieldset, the map comes first, with the "Ort eingeben"/"Suchen" row and the radius slider both rendered *below* it (not above, as originally built) — a deliberate reorder so the map is the first thing seen under the fieldset legend. "Meinen Standort verwenden" (geolocation, the same `useMyLocation()` as before) is a small `LocateFixed` (lucide-react) icon-button absolutely positioned *inside* the "Ort eingeben" input's right padding, rather than a separate labeled "📍 Mein Standort" button next to it — a more compact, established pattern (same idea as a search box's embedded clear/search icon).
- The small inline map (`h-56`/`h-40`) is too cramped to actually interact with once there are several result markers on it, so `location-radius-picker.tsx` also supports expanding it: a "⤢" button (bottom-right of the map — Leaflet's own zoom control already occupies top-left, and "✕ Karte ausblenden" occupies top-right, so this is the one free corner) sets `expanded`, which switches the map's **wrapper** div from normal in-flow layout to `fixed inset-0` — full-viewport fullscreen on mobile, `sm:inset-8 sm:max-h-[70vh] sm:max-w-4xl sm:rounded-2xl` (a centered, bordered box with breathing room to the screen edge) from `sm:` up — with a click-to-close semi-transparent backdrop (`fixed inset-0 bg-black/40`, a separate element behind it) rather than a fixed pixel height. A "✕ Karte verkleinern" button and Escape both close it too. This deliberately expands via an explicit button rather than "click anywhere on the map", since the map surface itself already needs clicks for panning/zooming/opening marker popups — an any-click-expands trigger would conflict with that. The expand button is styled to match Leaflet's own control buttons (`.leaflet-bar a`'s look: white 26×26px square, dark text, `box-shadow: 0 1px 5px rgba(0,0,0,.65)`) rather than the app's usual rounded surface buttons, so it visually reads as part of the map rather than as an unrelated app UI element floating on top of it.
- The "Ort oder Region eingeben" input has a debounced (350ms, minimum 3 characters) autocomplete dropdown backed by the same `/api/geocode?q=` proxy the plain "Suchen" fallback uses — up to 5 suggestions, keyboard-navigable (Arrow keys/Enter/Escape), with `onMouseDown={(e) => e.preventDefault()}` on each suggestion button so picking one with a click doesn't blur the input before the click registers (the standard combobox pattern for this). Picking a suggestion or clicking "Suchen" both funnel through `applyPlaceResult(lat, lng)`: it moves the marker, and — if the radius is still "Alle" (`radiusValue == null`) — defaults it to 50km (`RADIUS_STEPS.indexOf(50)`) rather than leaving a freshly-searched place still showing every result countrywide. Both paths then call `closeUiAndScrollToResults()`, which collapses the enlarged map back down, closes `/projekte`'s "Erweiterte Suche" (`document.getElementById("erweiterte-suche")`, a plain DOM query rather than prop-drilling into a sibling component, matching `ScrollToTopButton`'s existing `#ergebnisse` lookup) and scrolls to the results — `delayed = true` (only when the radius was just defaulted) waits 700ms before scrolling, since defaulting the radius also re-triggers the debounced auto-submit/navigation that refetches a now-filtered result set, and scrolling immediately would land on the still-unfiltered list a moment before it changes underneath the viewport.
- While expanded, the place-search input (`placeholder="Ort oder Region eingeben"`, plus the embedded `LocateFixed` icon) and the radius slider are rendered a second time as an `absolute inset-x-0 bottom-0` panel with a solid (not translucent) `bg-surface` background **overlaid on the bottom of the enlarged map itself**, not only below it — so they stay usable without shrinking the map back down first. Both call sites render the exact same `searchControls` JSX (a local variable holding that block, built once per render from the same controlled `placeQuery`/`radiusIndex` state) — normally below the map, or inside this overlay instead while `expanded`, never both at once — so toggling `expanded` can't leave two live copies of the same form controls in the DOM. Leaflet's own attribution control (default position bottom-right) would otherwise sit hidden behind this panel, so the `[mapVisible, expanded]` resize effect also calls `map.attributionControl.setPosition(...)`, moving it to `topleft` (stacking below the zoom control) while expanded and back to `bottomright` once collapsed.
  - **The div Leaflet actually calls `L.map()` on must keep a constant `className` string across every render.** `L.map(container)` adds its own classes (`leaflet-container`, `leaflet-touch`, ...) directly onto that element outside of React's knowledge; React's reconciler only re-applies the whole `class` attribute when the `className` *prop value* it computes differs from what it wrote on the previous render (it diffs against its own last-written value, not the DOM's actual current class list) — so as long as the JSX-computed string is identical to last time, React leaves the attribute alone and Leaflet's own classes survive untouched. The very first version of the expand feature broke this: it toggled that div's own className based on `expanded` (`"h-full w-full overflow-hidden"` vs. a fixed-height variant), so the moment someone expanded the map, React overwrote `class` with a string that didn't include `leaflet-container` — silently stripping Leaflet's base styling (the tile layer still rendered internally, positioned via inline `transform`s, but with no visible map surface at all). Fixed by moving every size/shape class (`h-56`/`h-40`/`rounded-xl`/the `fixed`-vs-`relative` toggle/etc.) onto the **wrapper** div one level up, which Leaflet never touches, and giving the actual `ref={mapRef}` div a hardcoded, always-identical `"h-full w-full"` className. The general rule this establishes: never let application state drive `className` (or anything else React fully owns) on a DOM node a third-party library also mutates directly — put reactive styling on a wrapper instead.
  - The same Leaflet container/instance is reused for both sizes (only the wrapper's CSS changes, no remount), so `invalidateSize()` plus a re-fit of the current view (selected-item focus or overview, see below) runs after every `mapVisible`/`expanded` transition, since Leaflet doesn't notice its container resizing on its own.
- Clicking the map does **not** set the search origin at all — there's no click handler for it. An earlier iteration required an explicit "📍 Standort auf Karte setzen" step (arming a `placementMode` so only the *next* click placed the marker) specifically to stop panning/zooming the results map from accidentally moving the origin, but once the origin could already be set via the place-name search or the `LocateFixed` geolocation icon (see above), that whole button/mode was dropped as redundant — a plain click on the map now just pans/zooms or interacts with markers/popups like any other Leaflet map, never the search origin.
- `fitOverviewView(L, map)` is the single place that decides what the map's view should show when no specific item is selected: the bounds of every result marker plus the search origin, **extended to always also include the full radius circle** when one is active. This replaced two independent `fitBounds` calls (one in the radius-circle effect, one in the results-layer effect) that used to race each other — moving the radius slider re-fetches a new (filtered) `resultItems` array a moment later, and whichever `fitBounds` happened to run last won, which could leave the circle only partially visible again right after it had just been fitted to it. Both effects now call this one function, so the circle is always included in the view regardless of which one fires last.
- `src/lib/category-color.ts` (`colorForCategory(id)`) deterministically hashes an `AttributeOption` id to one of eight warm-but-distinguishable colors (kept visually separate from the semantic success/warning/error tones so a category dot never reads as a status) — used to color-code "Veranstaltungsart" (event type) on the `/termine` calendar without needing a dedicated color column in the database. `/termine/page.tsx` builds a `Record<"YYYY-MM-DD", string[]>` from the already-fetched (filtered) `events` list and passes it through `termine-search-form.tsx` into `event-date-filter.tsx`, which renders up to 3 small colored dots under any day-cell that has matching events, plus a color legend (name + swatch, computed independently client-side from the same `veranstaltungsart` options via the same deterministic function, so it always matches without needing to be threaded through as extra data) below the calendar so the colors carry meaning rather than being purely decorative.
- `location-radius-picker.tsx` takes a `resultItems` prop (`MapResultItem[]` from `src/lib/map-result-item.ts` — `{id, label, sublabel?, type?, popupHtml?, latitude, longitude, href}`, plus the `escapeHtml` helper used when building marker popup/tooltip HTML); the found items are rendered as clustered markers **in the same map instance** as the origin pin/radius circle. Both `/projekte` and `/termine` use this merged single-map layout — there is no separate results map anymore. `renderResultsLayer(L, map)` (re)builds this marker-cluster layer and is called both from the mount effect (for the initial paint, since the map itself is only ready once the async `getLeafletWithCluster()` resolves) and from a `useEffect(() => {...}, [resultItems, selectedId])` — `resultItems` is a **new array on every filter-driven navigation** (each change to any filter re-renders the server-component page with a differently-filtered result set), so this dependent effect correctly rebuilds the layer every time a filter changes; an earlier version assumed the opposite (that `resultItems` "never usefully changes after mount") and only rendered once at mount, which silently left the map showing the very first load's markers forever regardless of later filtering — e.g. filtering down to 2 results still showed all the original markers. `location-radius-picker.tsx` always renders (even with zero geocoded items — it just falls back to a Germany-wide view) rather than being conditionally hidden, so newly published listings/events without coordinates yet don't suppress the map for everyone else's markers.
  - Each result marker's **permanent tooltip label is itself clickable**: `bindTooltip(..., { interactive: true })` (tooltips are non-interactive/`pointer-events: none` by default, which would otherwise let clicks fall through to the map underneath) plus `marker.getTooltip()?.on("click", () => marker.openPopup())` opens the marker's own popup. The popup itself uses `item.popupHtml` when the caller supplied one, otherwise falls back to a plain label+type link. `/projekte/page.tsx`'s `buildListingPopupHtml()` builds a small "business card" for listings: photo, project name (linked to the same inline `?projekt=<id>` detail pane via `item.href`), location, motto, Projekttyp/Kategorie badges, monthly cost, and a mini "Nächste Termine" list (up to 3, fetched in one batched `event.findMany({ listingId: { in: [...] } })` query rather than per-listing, each linked to its own `/termine/[eventId]` standalone page).
  - The marker cluster group also sets `spiderfyDistanceMultiplier: 3` and listens for its `spiderfied`/`unspiderfied` events to `closeTooltip()`/`openTooltip()` on the affected markers. Several markers can legitimately sit at (near-)identical coordinates (e.g. multiple events at the same listing's address), and clicking their cluster bubble while already at max zoom "spiderfies" them — fans them out a small fixed distance with connector legs — which isn't enough room for their *permanent* labels not to overlap into an unreadable mess; hiding labels for that brief fanned-out state (the markers are already visually separated and individually clickable/poppable without them) is simpler and more robust than trying to out-space the overlap.
- All map components use dynamic `import("leaflet")` inside `useEffect` (Leaflet touches `window` at module load, so it can't be a top-level import in code that might render on the server), plain `L.circleMarker` instead of the default pin icon for non-origin markers (sidesteps Leaflet's well-known marker-asset-path bug under bundlers), and a global `.ligem-event-label` CSS class in `globals.css` (Leaflet renders outside React's tree, so Tailwind utility classes don't reach it).
- **`leaflet.markercluster` bundler quirk**: its CJS build mutates the Leaflet *global* `L` directly (`L.MarkerClusterGroup = ...`) instead of `require("leaflet")`-ing its own reference, and the object returned by a dynamic `import("leaflet")` is a frozen ES module namespace object that can't have new properties added to it. `src/lib/leaflet-cluster.ts` (`getLeafletWithCluster()`) works around this with a **module-level singleton**: the first caller spreads the imported module into a plain mutable object, assigns it to `window.L`, awaits `import("leaflet.markercluster")` once, then caches that same object for every later caller. This isn't just cosmetic — `leaflet.markercluster`'s factory function only runs once per browser session (ES modules are cached), so if each map component created and discarded its own mutable copy instead of sharing one, only the very first mounted map would ever get a working `markerClusterGroup`; every later mount/remount (including plain re-renders and client-side navigations between `/projekte` and `/termine` within the same session) would silently get a copy missing the augmentation. `location-radius-picker.tsx` gets its `L` through this helper — use it for any new component that needs clustering rather than reimplementing the mutable-copy dance locally.
- **Kartenkacheln (`src/lib/map-tiles.ts`)**: both maps originally hotlinked `{s}.tile.openstreetmap.org` directly, which is explicitly **not** meant for production use — OSM's volunteer-run tile servers enforce a usage policy that actively blocks requests missing a `Referer` header (a real "Access blocked ... Referer is required by tile usage policy" tile image, `osm.wiki/Blocked`), reported directly: the map broke specifically on one Android browser (whose privacy mode strips the header more aggressively than others) while working fine elsewhere, and would eventually be liable to the same blocking on any browser/traffic volume regardless — this is OSM's own server-side policy, not something fixable from the app's side. `TILE_URL`/`TILE_ATTRIBUTION` switch to **MapTiler** (`https://api.maptiler.com/maps/streets-v4/{z}/{x}/{y}.png?key=...`, a provider meant for exactly this use case) whenever `NEXT_PUBLIC_MAPTILER_KEY` is set, falling back to OSM directly only when no key is configured at all (fine for a quick local look, not reliable for anything beyond that — get a free key at `cloud.maptiler.com` and set `NEXT_PUBLIC_MAPTILER_KEY` in the root `.env` for any real usage, including this project's own dev/staging). Both `location-radius-picker.tsx` and `address-fields.tsx` import `TILE_URL`/`TILE_ATTRIBUTION` from this one file rather than hardcoding a tile URL locally. Being a `NEXT_PUBLIC_*` var, it's inlined into the client bundle at build time — `docker-compose.yml`'s `web.environment` passes it through from the root `.env` (same pattern as `ANTHROPIC_API_KEY`), and since production's `docker-compose.prod.yml` runs `pnpm build` as part of the same container command chain (see that file's own comments), the variable only needs to be set in that container's environment *before* the build step runs, not baked in separately.
- **Global type scale reverted to Tailwind's stock defaults** (`globals.css`): an earlier user-requested reduction had shrunk `body`'s base font-size to `14.4px` and the whole `@theme inline` `--text-xs`–`--text-5xl` scale by the same ~20%, which put headings, form inputs, and labels under the 16px threshold iOS Safari uses to decide whether to auto-zoom the page on focus — reported directly as the page zooming in on every mobile form field. Both are back to Tailwind's actual default values (`body` at `16px`, `--text-base: 1rem`, `--text-lg: 1.125rem`, etc. — the exact numbers the ~20%-smaller values were computed from) per explicit follow-up request rather than trying to special-case just the affected controls. A global, `!important`-qualified rule (`input, select, textarea, label { font-size: 16px !important; }`) additionally forces exactly those four element types to 16px regardless of whatever Tailwind text-size utility class they carry (`text-sm`/`text-xs` are still 14px/12px even in the restored standard scale, and a class selector like `.text-sm` has the same CSS specificity as a plain element selector, so `!important` — not source order — is what guarantees this wins). `--spacing` (Tailwind v4's single base unit — every numeric utility, `p-*`/`m-*`/`gap-*`/`h-*`/`w-*`/`min-h-*`/etc., is `calc(var(--spacing) * N)`) is a separate, still-reduced variable (`0.19rem` vs. the 0.25rem default, ~24% smaller) untouched by this revert — it governs layout dimensions (checkbox/radio size, calendar grid, form-control heights), not font-size, and wasn't part of what caused the zoom issue. Checkbox/radio *label text* still gets an explicit `text-sm` className (the `"flex min-h-11 items-center gap-2"` wrapper pattern, used ~17x across `listing-form-fields.tsx`/`event-form-fields.tsx`/`*-search-form.tsx`/`registrieren`/`admin/attribute`/`admin/nutzer`) for its own reasons (it previously had no size class at all), but the label's actual rendered size now comes from the global `label { font-size: 16px !important }` rule above, not from that class.
- Media/photos/videos go through MinIO, not through Prisma directly: `src/lib/storage.ts` wraps the `minio` client (bucket `ligem-media`, auto-created on first use) with `putObject`/`getObjectStream`/`deleteObject`. Since MinIO is only reachable inside the Docker network (bound to `127.0.0.1` on the host), `src/app/api/media/[...path]/route.ts` proxies/streams objects to the browser (with HTTP Range support, see "Videos in der Galerie" below) — image `<img src>`s/`<video src>`s point at `/api/media/<storageKey>`, never at MinIO directly. `Media` belongs to either a `Listing` or an `Event` (`listingId`/`eventId` both nullable, exactly one set — enforced in application code, not the DB). `src/lib/media.ts` (`processAndStoreImage`, `splitBySize`) holds the shared photo-upload pipeline: resize with `sharp` at upload time into two stored JPEGs per photo — a display version (max width 1600) and a thumbnail (max width 400) — rather than resizing on every render; `src/app/projekte/[id]/media-actions.ts` (listings) and `src/app/projekte/[id]/termine/event-media-actions.ts` (events) both call it, each with their own ownership check. `Media.position === 0`'s thumbnail is the list-view image on `/projekte` and `/termine`. Files over 8MB are rejected per-file (`MAX_IMAGE_SIZE` in `src/lib/media.ts`); `next.config.ts`'s `experimental.serverActions.bodySizeLimit` is raised to `50mb` so the *framework's* 1MB-default request-body cap doesn't reject a multi-file batch before the per-file checks even run. Video uploads (see "Videos in der Galerie" below) go through a plain Route Handler instead of a Server Action specifically so this limit doesn't need to account for 200MB files.
- Domain shape (full rationale in project memory — `ligem_positioning`, `ligem_roles_and_content_model`, `ligem_trust_legal_business`, `ligem_tech_and_design`):
  - **Auth**: `User`/`Account`/`Session`/`VerificationToken` follow the Auth.js Prisma-adapter shape. `UserRoleAssignment` lets one user hold several of `SUCHENDE`/`ANBIETER`/`MODERATOR`/`ADMIN` at once (no fixed role). `User.lastLoginAt` is updated on every sign-in (see Authentication above); `User.image` doubles as both the OAuth-provided avatar and a self-uploaded one (see "Benutzerverwaltung" below).
  - **`ListingManager`** (Listing ↔ User, many-to-many) grants co-managers content-edit rights on a Listing beyond its original `createdById` — see "Benutzerverwaltung" below for the full rationale (why events don't need their own equivalent table, why the edit-rights level is deliberately more limited than the original owner's).
  - **Organizations** own multiple `Listing`s/`Event`s (Vereine/Genossenschaften as first-class actors, not just users).
  - **Listing** taxonomy (the "Art des Projektinserates" — Zimmer, ganze Einheit, ...) is DB-backed and many-to-many (`ListingCategory` + `ListingCategoryAssignment`), not a hardcoded enum. Only `projectName` + `createdBy` are required; everything else (Standort, Ansprechperson, Gruppengröße, Kosten, Suchzeitraum, ...) is optional real columns on `Listing`.
  - **Generic filter-attribute system**: `AttributeGroup` + `AttributeOption` is a general extensible-taxonomy mechanism sitting alongside `ListingCategory`, shared between Listings and Events via `AttributeGroup.appliesTo` (`LISTING`/`EVENT`) plus two separate join tables, `ListingAttributeOption` and `EventAttributeOption`. Listing-side groups: Projekt Typ, Projekt Status, Geschlechterverteilung, Organisationsform, Gemeinschaftsbereiche, Grundwerte, Wohnlage, Zielgruppe. Event-side groups: Veranstaltungsart, Zielgruppe, Merkmale. `AttributeGroup.allowMultiple` is a UI hint only for the listing/event **entry** form (radio vs. checkboxes when assigning attributes to a listing/event) — the underlying relation is many-to-many either way, so new filter values (or whole new filter groups, for either target type) are just rows, managed from `/admin/attribute`, never a migration. The **search-filter** forms (`/projekte`, `/termine`) deliberately ignore this flag and always render every group as a multi-select checkbox dropdown (see those entries below) — filtering by "any of several values" is useful even for a group where each individual listing/event only ever holds one. There is no free-form `Listing.attributes` JSON column — it was removed once this system replaced it.
  - No matching engine anywhere in the schema — `SavedSearch.filters` is just a stored filter set for the user's own search UI (not built yet).
  - `ContactRequest` (contact form, not chat) only reveals the listing owner's contact info once `status` flips to `ACCEPTED` — see "Kontaktanfragen" below for the owner-facing inbox this status now actually drives. `Appointment` is separate (Besichtigungstermin scheduling, not built yet). `Event` is the public calendar (Veranstaltungen/Besuchstage): listing owners manage their own under `/projekte/[id]/termine`, and everyone can browse/filter/search-by-radius the public calendar at `/termine`. Events carry `latitude`/`longitude` (plain columns, kept in sync with the `location` PostGIS point — see below), `websiteUrl`, `cost`, `maxParticipants`, `registrationRequired`; `EventRegistration` is the "send a message or sign up N participants" form on an event's public page — still no accept/decline workflow, the organizer just sees a list (`/projekte/[id]/termine/[eventId]/anmeldungen`), but it does have a `viewedAt` timestamp now (see "Kontaktanfragen" below) purely for the header nav's notification badge.
  - `Report` covers abuse reports across listings/events/orgs/users; there's deliberately no ban-history/audit subsystem, matching the "lightweight trust & safety" decision.
- Prisma also installed its own AI-agent skills under `apps/web/.claude/skills/prisma-*` (from `prisma init`) — check those for Prisma-7-specific syntax (driver adapters, config file shape) before assuming Prisma 5/6 patterns from training data.

## Authentication & authorization

`src/lib/auth.ts` configures Auth.js (`next-auth@5`) with `PrismaAdapter`, JWT sessions (required because of the Credentials provider), a `Credentials` provider (email + bcrypt-hashed password against `User.passwordHash`), and an optional `Google` provider gated on `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` being set. Route handler: `src/app/api/auth/[...nextauth]/route.ts`. An `events.signIn` hook updates `User.lastLoginAt` on every successful sign-in (Credentials and Google alike) — deliberately just this one timestamp, not a full login-history log (see "Benutzerverwaltung" below).
- `callbacks.jwt`/`callbacks.session` copy the user id onto `session.user.id` (not there by default with JWT sessions) — the type augmentation for this lives in `src/types/next-auth.d.ts`. Any code reading `session.user.id` depends on both files staying in sync.
- `src/components/site-header.tsx` is a server component that calls `auth()` directly. Logged out, the nav shows a single "Anmelden" entry ("Registrieren" isn't separate — `/anmelden` already offers it as an option). Logged in, the user's name (or email, if no name is set) is a native `<details>`/`<summary>` account-menu disclosure (same collapsed pattern as `MultiSelectDropdown`) containing "Mein Konto", "Meine Projekte", "Admin" (only when `isAdmin()` is true), and a sign-out `<form>` whose action calls the exported `signOut`. The disclosure itself is `src/components/account-menu.tsx`'s `AccountMenu` — a small **client** island (unlike the rest of `SiteHeader`), passed `displayName`/`admin`/a `signOutAction` prop (an inline server action declared inside `SiteHeader`'s own body, `"use server"`, then handed down — the same "Server Action passed as a Client Component prop" pattern used elsewhere for reorderable-photo-gallery's `.bind()`ed actions). This one piece needed to become a client component specifically so it can close itself after a click on one of its own items: a plain `<details>` has no such behavior on its own, and since `SiteHeader` persists across Next's client-side navigations (the same component instance isn't remounted when a `<Link>` inside it is clicked), the menu would otherwise stay visibly open over whatever page loads underneath it. `AccountMenu` holds a `ref` to the `<details>` and sets `.open = false` via a plain `onClick` on the wrapping content `<div>` that relies on ordinary event bubbling from every Link/submit button inside it — no `preventDefault()`, so navigation/sign-out still proceed exactly as before, this just also flips the disclosure closed.
- `src/lib/authz.ts` has the admin-role check (`isAdmin(userId)`, checking `UserRoleAssignment` for `ADMIN`) plus `requireAdminPage()`/`requireAdminAction()` — every `/admin/*` page and every admin server action calls one of these; the page-level check alone is not enough since actions can be invoked directly. `canManageListing(userId, listingId, listingCreatedById)`/`canManageEvent(userId, event)` are the shared content-edit-rights checks used by every `/projekte/[id]/**` page/action and both video-upload Route Handlers — see "Mitverwalter:innen" below for what they check beyond plain ownership.

## Benutzerverwaltung (`/mein-konto`, Mitverwalter:innen, `/admin/nutzer`)

`/mein-konto` is the self-service counterpart to the admin-only `/admin/nutzer` — every logged-in user can manage their own account there (reached from the header's account-menu dropdown, see above), backed by `src/app/mein-konto/actions.ts`:

- **Profilbild**: reuses `User.image` (the standard Auth.js/PrismaAdapter field, auto-populated from Google's profile for OAuth sign-in) rather than a new column — for a self-upload it holds an `/api/media/<key>` proxy path exactly like every other MinIO-backed image in this app, so the same `<img src>` works regardless of whether the value came from Google or from an upload. `storeAvatar(file, userId)` (`src/lib/media.ts`) resizes to a fixed 256×256 **square crop** (`fit: "cover"`, unlike gallery photos which keep their own aspect ratio) under `users/<userId>/` — a deliberately simpler pipeline than `processAndStoreImage()` since an avatar needs only one size, no separate thumbnail. Uploading a new one deletes the previous MinIO object first, but only if it was one of ours (`image` starts with `/api/media/users/`) — a Google-provided avatar URL isn't ours to delete.
- **Persönliche Daten**: name (optional) + email. Changing the email has no verification step (there's no email-verification system in this app at all yet — a suggested-but-not-built future addition); a duplicate email is caught via the `User.email` unique-constraint violation, not a separate pre-check query.
- **Passwort ändern**: only rendered when `User.passwordHash` is set (a Google-only account has none) — current password verified via `bcrypt.compare` before hashing and storing the new one (`bcrypt.hash(..., 12)`, matching `/registrieren`'s rounds). Both new-password fields use the same `PasswordField` component `/anmelden` uses for its eye-icon toggle.
- **Mitverwalter:innen** (`ListingManager` in schema.prisma): a listing's original creator can grant a second (or third, ...) user content-edit rights on it by email, and revoke them again — `addListingManager`/`removeListingManager`, both gated by a `requireListingOwner` check (the *original creator specifically*, stricter than `canManageListing` — an existing co-manager cannot add/remove other co-managers, only the creator or an ADMIN can, matching the product decision that co-managers get edit rights only). A `Listing`'s events automatically inherit its managers too (no separate `EventManager` table) — sharing a project also shares its calendar, so `canManageEvent` falls back to checking the event's `listingId` against `ListingManager` whenever the event's own `createdById` doesn't match. `/mein-konto` shows both directions: the creator's own listings with their current manager lists (add/remove forms), and, separately, any listings the viewer co-manages on someone else's behalf (read-only, links to the edit page). `/meine-projekte` merges both into one list (`OR: [{ createdById }, { managers: { some: { userId } } }]`) with a "Mitverwaltet" badge distinguishing the two. `/termine/neu`'s listing-picker query got the same `OR` treatment, since a co-manager can create events for a listing they don't own.
- **`/admin/nutzer`** additionally shows, per user, a collapsed `<details>` "Projekte (N) & Termine (N)" summary (native disclosure, not client JS) listing that user's own listings (with status and a "N Mitverwalter" badge whenever `_count.managers > 0` — this is how an admin spots a listing/event with more than one person attached, per product requirement) and events, plus a separate "verwaltet N fremde(s) Projekt(e) mit" list for listings they co-manage. The existing "letzter Login" line next to each user's email reads `User.lastLoginAt` (or "Noch nie eingeloggt").

## Pages

All *mutating* forms follow the same convention: a server-component page with a plain `<form action={serverAction}>` (no client JS/`useActionState`), where the action is a `"use server"` function in a sibling `actions.ts` that validates, mutates via Prisma, and calls `redirect()` — errors redirect back to the same page with an `?error=...` query param the page reads server-side. This works without JavaScript and keeps forms accessible; follow the same pattern for new forms rather than introducing client-side form state. The large "Projekt eintragen"/"Projekt bearbeiten" field set is factored into the shared `src/components/listing-form-fields.tsx` so create and edit stay in sync — extend that component, not one page's copy of it, when adding a field. Every `AttributeGroup` field in `ListingFormFields`/`EventFormFields` (and the `ListingCategory` "Art des Projektinserates" checkboxes) renders via the shared `src/components/multi-select-dropdown.tsx` (`MultiSelectDropdown` — same collapsed `<details>`/`<summary>` "field name, then click to expand and pick" presentation as the search-filter sidebars, see `/projekte`/`/termine` below) with its `multiple` prop set from that group's own `allowMultiple` flag (radios for a single-value group, checkboxes for a multi-value one) — unlike the search forms, which always force `multiple` regardless of the flag, the entry form still enforces each group's real single-vs-multi-value semantics when assigning attributes to a listing/event; only the collapsed-dropdown *look* is shared between the two contexts.

`MultiSelectDropdown` takes two more optional props, both only ever passed by search forms (never by `ListingFormFields`/`EventFormFields`): `counts?: Record<string, number>` appends "(N)" after each option's name and grays out both the label text and the checkbox/radio itself (`text-text-muted/40`/`opacity-40`) when `N === 0`; `onChange?: () => void` is called after the summary chip's own small "✕" clear button (see below) resets the group back to no selection, mirroring `LocationRadiusPicker`/`EventDateFilter`'s existing `onChange` convention for state changes that don't originate from a native DOM change event (`setSelected(new Set())` unchecks every input via React's controlled `checked` prop, but that's a state update, not a user interacting with a checkbox, so it never fires a native `change` event for the surrounding form's `onChange`-bubbling auto-submit to pick up — the explicit callback is the only way that reset actually re-submits the search). The "✕" itself sits absolutely positioned at the top-right corner of the "N ausgewählt" summary chip (`-right-1.5 -top-1.5`, a small circular badge overlapping the chip's corner) and calls both `e.preventDefault()`/`e.stopPropagation()` first, since without that a click landing anywhere on the `<summary>` row would also toggle the surrounding `<details>` open/closed via the browser's own default behavior for that element.

`/projekte/page.tsx`'s "Erweiterte Suche" additionally computes real faceted counts for every checkbox across `ListingCategory` and every advanced `AttributeGroup` — not each option's raw overall total, but how many results selecting *that specific option* would produce once combined with every other currently active filter (typ/kategorie/other attribute groups/Suchzeitraum/`suche`/radius), so an unchecked "In Gründung" showing "(7)" means checking it right now would narrow the current result set to 7, and an option a listing search can't currently satisfy at all shows "(0)" and renders grayed out via the `counts` prop above. Computed as one query per facet group (`categoryCounts`/`attrCounts`, built via a local `facetWhere(excludeGroupSlug, excludeKategorie)` helper that rebuilds "every filter except this one group's own") rather than one query per option — each query fetches the candidate listings' own option/category assignments for just that group, and the per-option count is then a plain JS filter over that already-narrow candidate set testing `{already-selected ids in this group} ∪ {this option}` (OR-widening, matching how the actual `some: { optionId: { in: [...] } } }` filter behaves once this option is also checked) — so this stays at a fixed number of extra queries (one per group) regardless of how many options a group has. `/termine/page.tsx` has the identical mechanism for Veranstaltungsart/Zielgruppe (`artCounts`/`zielgruppeCounts`, its own local `facetWhere(excludeGroup)` — only two groups there, so it's a plain `"art" | "zielgruppe"` parameter rather than a per-slug record).

Within `ProjekteSearchForm`'s "Erweiterte Suche", the "Suchzeitraum" fieldset is the *first* field (before "Art des Projektinserates" and every attribute group) — it used to sit between them, but a filter that narrows by date is reached for more often than any single attribute checkbox, so it goes first.

The `/projekte` and `/termine` **search/filter** forms are a deliberate exception — they don't mutate anything, so they auto-apply on every change instead of requiring a submit click. `src/lib/use-auto-submit-form.ts` (`useAutoSubmitForm()`) is the shared piece: it holds a `formRef`, and its `submitNow()` reads the form via `new FormData(formRef.current)`, builds a query string, and calls `router.replace(pathname + "?" + qs, { scroll: false })` (wrapped in `startTransition` for `isPending`), so the server component page re-fetches and re-renders without a full page reload; `handleChange()` is the same thing debounced 300ms, wired to the form's own `onChange` (native `<select>`/checkbox/radio changes bubble up to it for free). `src/components/projekte-search-form.tsx` and `src/components/termine-search-form.tsx` are client components that own the entire filter `<form>` (moved out of the respective page files, which stay server components and just pass in serializable data + current param values as `defaults`) — they have no submit button, and set `onSubmit={(e) => e.preventDefault()}` as a safety net (the "Ort eingeben" text field inside `LocationRadiusPicker` could otherwise implicit-submit on Enter). `LocationRadiusPicker` and `EventDateFilter` both take an optional `onChange?: () => void` prop, invoked (skipping the initial mount, via a ref guard) whenever their internal state changes through map clicks, place search, geolocation, the radius slider, calendar day clicks, or the date-range preset buttons — none of which are native DOM "change" events on the hidden inputs they update, so they can't rely on the form's own bubbling `onChange` and must call this callback explicitly instead.

Both pages also share the same responsive two-column layout: a page-level wrapper (`max-w-[1800px]`, no narrower cap — unlike every other page's `max-w-2xl`-ish wrapper, these two are meant to use the full browser width on desktop) contains a `flex flex-col lg:flex-row` split — a fixed sidebar column for the search form (map included) and a `flex-1 min-w-0` column for results. Below `lg`, it's a single stacked column (form above results) matching every other page's mobile-first layout; nothing here is sticky. The result `<ul>` itself switches from `grid-cols-1` to `xl:grid-cols-2` — a second breakpoint step, one narrower than the page-level split — since right after the page splits into two columns the results column alone often isn't wide enough yet for two result cards side by side without feeling cramped.

Both `/projekte/page.tsx` and `/termine/page.tsx` keep their sidebar at `lg:w-[380px]`, deliberately narrow so the results column gets as much of the page's width as possible — `termine-search-form.tsx` stacks `EventDateFilter` above `LocationRadiusPicker` as plain siblings (not a side-by-side grid) specifically to keep that sidebar narrow rather than needing extra width to fit a calendar and a map next to each other. Within `event-date-filter.tsx`, the "Zeitraum" heading and the "Nächste 7 Tage"/"Nächste 30 Tage"/"Alle anstehenden" preset buttons are rendered as a sibling block *after* the bordered calendar box (not before), so they visually sit directly under the calendar; the radius slider inside `LocationRadiusPicker` already sits under the map by virtue of that component's own internal layout.

The sidebar `<form>` (`ProjekteSearchForm`/`TermineSearchForm`) and the results column start flush at the same height — the form previously carried its own stray `mt-8` (a leftover from an earlier layout), which pushed the whole sidebar noticeably lower than the results heading/detail pane next to it; removed, since the shared two-column wrapper div already provides the gap from the page intro above both columns. The **results column itself** (not the two-column wrapper) carries `id="ergebnisse"` (plus `scroll-mt-4` for a little breathing room), and `buildProjekteHref`/`buildTermineHref` unconditionally append `#ergebnisse` to every URL they build (selecting a result, stepping prev/next, going back to the list) — so every such navigation lands the browser right at the top of the results/detail pane instead of the very top of the page. Without this, Next's default Link scroll-to-top behavior scrolls past the h1/intro text every single time, which reads like a repeating hero banner when quickly stepping through prev/next; anchoring to `#ergebnisse` keeps that intro text out of the way once you're actually browsing, landing at a consistent scroll position every time. **The anchor must live on the results column, not the wrapper** — on desktop (`lg:flex-row`) both columns start at the same height so either placement looks identical, but below `lg` the layout stacks (sidebar/filter form above results), so anchoring at the wrapper's top used to land the scroll position at the top of the *filter sidebar* on mobile, forcing the user to scroll past the whole form again to reach the actual detail pane; anchoring at the results column directly fixes this for both breakpoints at once.

A separate site-wide `src/components/scroll-to-top-button.tsx` (`ScrollToTopButton`, client component, rendered once in the root `layout.tsx` next to `DemoDataRibbon`) is a fixed circular button in the bottom-right corner of every page — appears only once the user has scrolled down more than 400px. On click, it looks for an element with `id="ergebnisse"` on the current page (`document.getElementById`) and, if present, `scrollIntoView`s to it (respecting that element's own `scroll-mt-4`, exactly like hash navigation) — the same target the Weiter/Zurück-Blättern links above already scroll to — rather than jumping past it all the way to `y=0`; on every other page (no such anchor) it falls back to a plain scroll to the very top of the page.

## Demo data generators

The core generator logic lives under `apps/web/src/lib/demo-data/` (`shared.ts`, `listings.ts`, `events.ts`, `long-description.ts`, `cleanup.ts`) and creates synthetic, clearly-fake `Listing`/`Event` rows (with real photos from Lorem Picsum, real geo-spread across both 32 real big German/Austrian/Swiss cities and 20 real small villages/towns, and randomized attributes/categories) to exercise the `/projekte` and `/termine` search and filter UI at realistic volume. It exists because scraping real communities' data from other platforms for this purpose would raise ToS, copyright, and GDPR/consent problems — synthetic data sidesteps all of that.
- **Every generated project name/motto/"So leben wir"/"Wen wir suchen" and every event title/description is unique**, not picked from one small fixed pool. `listings.ts`/`events.ts` compose each value from several independent word/sentence banks (e.g. `NAME_STEMS` × `NAME_SUFFIXES` for names, `ABSURD_TOPICS` × a per-theme title template for events) — each bank entry is a grammatically self-contained fragment (a whole sentence, or a whole compound-noun part), so any recombination stays coherent; there's no mid-sentence word-swapping that could produce broken German. `pickUniqueComposed(build, used)` in `shared.ts` retries the `build()` closure until it produces a string not already in `used` (a few hundred attempts against a combinatorial space in the thousands essentially never exhausts it) and adds it; `used` is seeded from values already in the database (not just the current batch), so generating another batch later still can't collide with what's already there.
- `shared.ts`'s `pickLocation()` picks a listing's location from either `CITIES` (32 big cities) or `VILLAGES` (30 small real villages/towns, added so demo listings aren't all clustered in major cities), weighted 88% village/12% city — raised twice from an original 45/55 split (then 60%, then this) since each prior weighting still read as too city-heavy in practice; note this only reshapes newly generated listings; the already-accumulated dataset keeps whatever mix it was generated with until cleared and regenerated via `/admin/demo-daten`.
- **`howWeLive`/`whoWeAreLooking`/event `description` are generated as HTML**, not plain text — matching what a real submission through `RichTextField` (see below) would produce, and using only tags its sanitizer allows (`p`, `strong`, `em`, `u`, `h2`, `h3`, `blockquote`, `ul`, `ol`, `li`, `br`): `long-description.ts`'s `buildLongDescriptionCandidate()` wraps the intro/building/people/closing sections in `<p>`s separated by `<h3>Das Zuhause</h3>`/`<h3>Die Menschen hier</h3>` subheadings, renders the theme's illustrative "Zuletzt gab es eine Diskussion…" vignette (present on the nine substance-themes, see below) as a `<blockquote>` instead of plain text, and wraps the closing paragraph in `<u>`; `listings.ts`'s `buildWhoWeSeekCandidate()` renders as a two-item `<ul>` when both sentence slots roll a value, otherwise a single `<p>`; `events.ts`'s `buildDescriptionCandidate()` wraps `kurz`/`ganztag` descriptions in one `<p>` (with the occasional detail sentence wrapped in `<u>`), and gives `mehrtaegig` (multi-day) events an `<h3>Programm</h3>` heading followed by a real `<ol>` day-by-day program instead of the previous newline-joined plain text.
- **"So leben wir" is a long (~200-400 word), deliberately absurd/over-the-top narrative**, generated by `long-description.ts`'s `buildLongDescriptionCandidate(cityName, isVillage)` rather than the old three-short-sentence system. It picks one random `Theme` (each with its own `opener`/`building`/`people`/`closer` sentence banks) and composes: 1 opener, 2 region-flavor sentences (a separate `VILLAGE_REGION_FLAVOR`/`CITY_REGION_FLAVOR` bank depending on `isVillage`, so the prose frames the location as rural or urban correctly), 4 building and 4 people sentences (via `pickNDistinct`, so a single generated text never repeats a sentence), and 2 closers — enough sentences to reliably land in the 200-400 word target given each bank's sentence length. The content deliberately centers on **communal-living substance rather than individual hobby/personality gimmicks** (an earlier version leaned on things like a music-genre-obsessed theme, which read as too gimmicky and got replaced): `kooperation` (mutual aid), `wertschaetzung` (appreciation & care), `achtsamkeit` (mindfulness), `konflikte` (conflict handling), `entscheidungsfindung` (consensus/discourse), `rechte-privilegien` (fairness/equity), `alltag-aktivitaeten` (shared daily-life planning), `ernaehrung` (food/dietary preferences), `politik-gesellschaft` (political/societal discourse) — plus a handful of lighter personality-flavor themes (`handwerk`, `yoga`, `spirituell`, `okkult`, `sekte`, `spiessig`, `nerd`) kept for variety. Each theme's `people` bank includes a short illustrative "Zuletzt gab es eine Diskussion darüber, ob …" vignette, so the text shows concrete examples of the group actually discussing these topics rather than just asserting the theme abstractly.
- **Event titles/descriptions intentionally span a much wider range of absurdity** than the original "esoteric commune" flavor alone: `ABSURD_TOPICS` (events.ts) now also covers Garten, Waldbaden, harmless kleinteilige Schwurbel-Satire (mundane things like the laundry schedule or a missing garden fork dressed up in conspiracy-theory language — deliberately not referencing real harmful conspiracy ideologies), legal-and-tasteful alternative-scene topics (Tantra, Kuschelparty, Polyamorie, FKK), and absurd hobby/animal combinations (dinosaur riding, keeping an orca in the bathtub, alpaca yoga) — all still just entries in the same shared pool used by `infotag`/`workshop`/`vortrag`/`online` titles, plus smaller additions to `MITMACHTAG_ACTIONS`/`BESUCHSTAG_TOPICS`/`FEST_OCCASIONS`.
- **Primary way to run it: `/admin/demo-daten`** (ADMIN-only, linked from `/admin`). The "Demo-Projekte generieren"/"Demo-Termine generieren" forms show a live progress bar while a batch runs, since generating even a modest count can take minutes (each row fetches a photo and writes several related rows) — far too long to hold a single request/response open. This is the one pair of mutating forms in the app that isn't a plain `<form action={...}>` (see the convention described under Pages): `src/components/demo-data-generate-form.tsx` (`DemoDataGenerateForm`, client component) calls a `start(count)` server action directly (`startGenerateListings`/`startGenerateEvents` in `src/app/admin/demo-daten/actions.ts`), which clamps the count, creates a job via `src/lib/demo-data/progress-store.ts`, and schedules the actual `generateDemoListings`/`generateDemoEvents` call inside `after()` (from `next/server`) — Next's sanctioned way to keep work running after the response has already been sent, rather than a bare unawaited async IIFE. `startGenerate*` returns the job id immediately; the client then polls a second action, `getGenerateProgress(jobId)`, every 700ms and renders a progress bar + "`completed / total`" text (plus the most recent item's label) until the job reports `done`, then calls `router.refresh()` to pull the updated demo-data counts. `progress-store.ts` is a plain module-level `Map<string, ProgressState>` — deliberately not Redis/Valkey-backed, since the app runs as a single long-lived Node process (`pnpm start`, not serverless) and this is a low-stakes admin dev tool; jobs are pruned a few minutes after completion. `generateDemoListings`/`generateDemoEvents`'s `onProgress` callback signature is `(current, total, message)` (numeric, not a pre-formatted string), used both by the admin UI's job store and by the CLI scripts' plain `console.log`. A third, destructive form calls `deleteAllDemoData()` behind a `ConfirmSubmitButton` (`src/components/confirm-submit-button.tsx`, a thin client-side `confirm()` wrapper used for the few genuinely irreversible admin actions) — this one stays a normal blocking form action, since deletion is fast enough not to need progress feedback.
- Each listing gets **3-6 photos** (`randomInt(3, 6)` in `listings.ts`, up from 1-2), enough to exercise the real multi-photo gallery (see `PhotoGallery` under Pages) rather than always hitting its single-photo fallback.
- **`searchPeriodStart`/`searchPeriodEnd`** are generated as a realistic pair rather than two independently-random dates: a start date (`chance(0.7)` of having one at all) plus either a week-length window, a month-length window, or no end date at all (an open-ended "looking from this date onward") — see the `periodLength` pick in `listings.ts`. This feeds `/projekte`'s "Suchzeitraum" advanced-search filter (see Pages).
- Every `Listing` created by the generator gets `isDemo: true` — this (not the historical email-domain check) is the source of truth for "is this demo data" everywhere in the app now, including the moderation queue below.
- Demo `User` accounts additionally get an email on the IANA-reserved `.invalid` TLD (`@ligem-demo.invalid`). **`Listing.createdById`/`Event.createdById` are `ON DELETE RESTRICT` in the actual database, not cascade** — a plain `DELETE FROM "User"` fails the moment any demo Listing/Event still references it. `deleteAllDemoData()` therefore deletes demo Events, then demo Listings, then the Users themselves, in that order (Media/attribute-option/category rows hanging off Listings/Events *do* cascade per schema.prisma, so those disappear automatically; the actual MinIO objects behind Media rows don't, and are deleted manually before the rows are removed).
- `apps/web/scripts/generate-demo-listings.ts` and `generate-demo-events.ts` still exist as thin CLI wrappers around the same `src/lib/demo-data/*` functions, for bulk/scripted use outside the browser:
  ```bash
  docker compose exec web sh -c "cd /workspace/apps/web && pnpm exec tsx scripts/generate-demo-listings.ts --count=50"
  docker compose exec web sh -c "cd /workspace/apps/web && pnpm exec tsx scripts/generate-demo-events.ts --count=100"
  ```
  `generate-demo-events.ts` only attaches events to existing demo listings (`isDemo: true`), so run the listings script (or the admin form) first. Listing counts are clamped to 1-100, event counts to 1-200.
- Since the `isDemo` column was added after some demo listings already existed in this project's dev database, they were backfilled once via `UPDATE "Listing" l SET "isDemo" = true FROM "User" u WHERE l."createdById" = u.id AND u.email LIKE '%@ligem-demo.invalid' AND l."isDemo" = false;` — not needed going forward since the generator sets the flag itself.

### Bulk actions (`/admin/projekte`, `/admin/termine`, `/admin/nutzer`)

Demo listings/events/users show a small amber "Demo" badge next to their name (`listing.isDemo`; for events via `event.listing?.isDemo` since `Event` has no `isDemo` column of its own; for users via the `@ligem-demo.invalid` email domain check, `DEMO_EMAIL_DOMAIN` from `src/lib/demo-data/shared.ts`). Each row has a checkbox (`name="listingIds"`/`"eventIds"`/`"userIds"`, `data-demo="true"` when applicable); a "Nur generierte auswählen" link (plus "Alle auswählen"/"Auswahl aufheben") toggles them via plain DOM queries in `src/components/bulk-select-controls.tsx`, a client component shared by all three pages — it selects purely by `form="<formId>"`, skipping `disabled` checkboxes, which is what lets it work across three different checkbox `name`s without modification. These checkboxes are **not** nested inside a `<form>` that wraps the list — each row already has its own single-item form(s) (`Freigeben`/`Ablehnen`/`Archivieren` on the first two pages, the roles-checkbox `Speichern` form on `/admin/nutzer`), and a literal nested `<form>` would be invalid HTML (the browser silently breaks it). Instead there's one outer bulk `<form id="bulk-projekte-form">`/`"bulk-termine-form"`/`"bulk-nutzer-form"` rendered once above the list, and every checkbox/bulk-button references it via the HTML `form="..."` attribute, which associates a control with a form anywhere in the document regardless of DOM nesting. The bulk buttons are plain submit buttons with different `formAction`s pointing at the respective `bulkReject*`/`bulkArchive*`/`bulkDelete*`/`bulkAddRole`/`bulkRemoveRole` functions in each route's `actions.ts` — a single `<form>` can route to different server actions per submit button this way. Bulk delete (unlike reject/archive/role changes, which are reversible) is a hard `deleteMany` and goes through `ConfirmSubmitButton`.

`/admin/termine` mirrors `/admin/projekte`'s structure exactly (same status tabs, same bulk-form pattern, same components) but defaults to the "Veröffentlicht" tab rather than "Wird geprüft" — Events are created as `PUBLISHED` directly with no moderation gate (see Pages above), so "Wird geprüft" is normally empty; this page exists purely to let admins reject/archive/delete events *after* the fact. `Event` has no `moderationNote`/`moderatedById` columns (unlike `Listing`), so its reject action has no note field.

`/admin/nutzer`'s bulk row has a role `<select>` plus "Rolle hinzufügen"/"Rolle entfernen" buttons (`bulkAddRole`/`bulkRemoveRole` — additive/subtractive on one role at a time across the selection, unlike the per-user form below it which replaces that one user's whole role set) alongside "Ausgewählte löschen" (`bulkDeleteUsers`). Two safety details specific to acting on user accounts:
- **You can never bulk-act on your own account**: the checkbox for the signed-in admin's own row is rendered `disabled` (so it's excluded from form submission regardless of any JS toggling — `BulkSelectControls` also skips `disabled` checkboxes so "Alle auswählen" doesn't even visually check it), and every bulk action additionally filters the acting admin's own id out of the submitted ids server-side (`selectedIds(formData, session.user.id)` in `actions.ts`) as defense in depth.
- **`bulkDeleteUsers` does not cascade a user's real content away.** `Listing.createdById`/`Event.createdById` are `ON DELETE RESTRICT` (see Demo data generators below) — deleting a user who still owns Listings/Events throws, which is caught and turned into the friendly `?error=besitzt-inhalte` message rather than silently wiping their projects/events as a side effect of an account deletion, or crashing the request. Users with no owned content delete cleanly.

## Cookie-Einwilligung für externe Video-Einbettungen

Of every external service this app calls (MapTiler/OSM map tiles, Nominatim geocoding, Google OAuth, Cloudflare Turnstile, the Anthropic KI-Import call, SMTP), only an embedded YouTube/Vimeo player (see "Video-Links" above) sets non-essential third-party cookies on its own — the rest are either technically necessary for a feature the visitor is actively using (map/search), or only ever triggered by an explicit action (clicking "Mit Google anmelden", submitting the contact form, an owner clicking "KI-Import"). So rather than a full multi-category consent-management platform, this is a single yes/no flag, scoped to exactly that one case.

- **`src/lib/cookie-consent.ts`**: `getVideoEmbedConsent()`/`setVideoEmbedConsent()` read/write a single `localStorage` key (not a cookie itself — nothing here needs to be server-readable); `subscribeVideoEmbedConsent(callback)` is a `useSyncExternalStore`-compatible subscription (listens for both a custom same-tab change event, since native `storage` events don't fire on the tab that wrote them, and the native cross-tab `storage` event). Both `CookieConsentBanner` and `PhotoGallery` read the flag via `useSyncExternalStore(subscribeVideoEmbedConsent, getVideoEmbedConsent, () => null)` rather than a `useEffect(() => setState(read()))` on mount — the React-recommended pattern for external mutable state like `localStorage`, since it avoids both the "setState synchronously in an effect" lint warning and a server/client hydration mismatch (the `getServerSnapshot` argument returns `null`, matching what the server always renders).
- **`src/components/cookie-consent-banner.tsx`** (rendered once in root `layout.tsx`, alongside `DemoDataRibbon`/`ScrollToTopButton`): a fixed bottom banner shown only while the flag is unset, with "Nur notwendige" / "Externe Videos erlauben" buttons and a link to `/datenschutz#externe-dienste`. Disappears for good once a decision is made (no re-prompting).
- **`photo-gallery.tsx`'s lightbox** gates the `isVideoLink` `<iframe>` behind this flag: if not globally allowed, it shows a click-to-load placeholder (provider notice + "Einmal laden" — allows just this one video for the current page view via local component state, not persisted — and "Immer erlauben" — persists the global flag, so future videos load directly) instead of the real embed. `src/lib/video-link.ts`'s `toEmbeddableUrl()` also rewrites YouTube URLs to `youtube-nocookie.com` (YouTube's own privacy-enhanced embed domain) as defense in depth, independent of the consent gate.
- **`/datenschutz`**'s `#externe-dienste` section (see below) documents this alongside every other external service.

## `/projekte` and `/termine` master-detail (inline preview panes)

Clicking a result on `/projekte` or `/termine` loads that listing's/event's detail **inline in the same right-hand results column** instead of navigating to the standalone `/projekte/[id]`/`/termine/[eventId]` page — the filter sidebar (and its map/calendar) stays mounted and untouched. This is a query-param mechanism, not a Next.js parallel/intercepting route: each `page.tsx` reads a `?projekt=<id>`/`?termin=<id>` search param and, when present and the item is visible to the viewer (`PUBLISHED`, or for listings also owner/ADMIN via the same `canManage` check as the standalone page), fetches and renders it via `<ListingDetail>`/`<EventDetail>` instead of the results `<ul>`; an invalid/inaccessible id is silently treated as "no selection" (falls back to the list) rather than erroring the whole page. `buildProjekteHref`/`buildTermineHref` (`(params, overrides) => string`, one per page.tsx) build a `/projekte?...`/`/termine?...` URL from the *current* search params with `overrides` applied (a value of `undefined` removes that key) — every result card/map-marker link uses it with `{ projekt: id }`/`{ termin: id }` so the rest of the active filters/map position survive the "navigation" (it's a normal same-route Link, not JS state), and each detail component's "← Zurück zur Liste" link uses it with that key set to `undefined`. Both href-builders also explicitly clear the page's transient flash param (`kontakt`/`angemeldet`) whenever selecting a *different* item or going back to the list — otherwise a stale "message sent" success banner would carry over and show again for an item whose form was never actually just submitted.

`src/components/listing-detail.tsx` (`ListingDetail`) / `src/components/event-detail.tsx` (`EventDetail`) hold the actual detail content (status banner, photo grid, description fields, attributes, contact/registration form, ...) — each is shared between its standalone page and its inline pane, parameterized by `returnTo` (where the contact/registration form's server action redirects back to after submitting — the standalone page passes its own fixed path, the inline pane passes the full current `/projekte?...`/`/termine?...` URL including the selection param) and an optional `backHref` (only set for the inline pane). `submitContactRequest` (`projekte/[id]/actions.ts`) and `submitEventRegistration` (`termine/actions.ts`) both read `returnTo` from a hidden form field and validate it's a same-origin path under their own route (`sanitizeReturnTo`, one per file) before redirecting there, since it's client-supplied.

**Cross-links between a listing's and an event's detail view always point at the inline `?projekt=`/`?termin=` pane, never at the other one's standalone page.** `EventDetail`'s "Veranstaltet von {Projektname}" link goes to `/projekte?projekt=<id>` (not `/projekte/<id>`), and `/projekte/page.tsx`'s map-popup "Nächste Termine" mini-list does the same for its own links — landing on either standalone page instead would silently drop that page's entire filter sidebar (search form, map/calendar), which is a real, previously-reported bug class rather than a stylistic preference. A brief attempt at making `EventDetail`'s link go to the standalone `/projekte/<id>` page instead was reverted for exactly this reason (reported directly: the sidebar was missing there). `ListingDetail`'s "Termine" list is the one deliberate exception per explicit product decision: its links go to `/termine#termin-<id>` (a bare list, not the `?termin=` detail pane), landing on the plain `/termine` overview scrolled to that event's own card (`id={`termin-${event.id}`}` + `scroll-mt-4` on each `<li>` in `/termine/page.tsx`, the browser's native hash-scroll needs no extra JS) — clicking a Termin from a project page is meant to show *where that event sits among all upcoming Termine*, not jump straight into its full detail view (still one click away, same as any other list item).

### Selected-item marker on the map

`location-radius-picker.tsx` accepts an optional `selectedId` prop (matching a `resultItems` entry's `id`) — both page.tsx's pass the current `?projekt=`/`?termin=` value straight through (via `ProjekteSearchForm`/`TermineSearchForm`). When set, the matching item is rendered with its own distinct, larger pin (`createSelectedPinIcon` — secondary/green `SELECTED_PIN_SVG`, visually distinct from both the small primary-colored result dots and the primary-colored "search from" origin pin) added **directly to the map**, not into the `markerClusterGroup` — so it's never hidden inside a cluster bubble regardless of zoom level, and stays correct even while a detail is open, since it's rebuilt by the same `[resultItems, selectedId]` effect described above (see `renderResultsLayer`) whenever either changes. Since the selected item already gets this dedicated marker+label, `renderResultsLayer` skips binding a permanent tooltip on that same item's regular marker inside the cluster group — otherwise the selected item would show two overlapping labels for the same spot (its normal cluster-group label plus the dedicated selected-marker label).

Selecting an item also zooms the map to a ~20km view centered on it (`renderSelectedMarker`'s `focusCircle`/`fitBounds` in `location-radius-picker.tsx`), computed via a throwaway `L.circle({ radius: 20_000 })`'s bounds rather than a fixed zoom level, since the zoom that shows "20km on screen" varies with latitude and viewport size. **That circle must be added to the map before calling `.getBounds()`** — Leaflet's `Circle.getBounds()` reads back the circle's own projected screen position (`this._map`/`this._point`), which are only set once it's actually on the map — so it's added, `.getBounds()` is read, and it's removed again immediately (never visibly rendered, just used for that one computation). Deselecting (going back to the list) zooms back out to the overview — the bounds fitting every result + the search origin, captured once at mount into `overviewBoundsRef` — rather than leaving the map stuck on the last-viewed item.

### Prev/next navigation within the inline detail pane

Both `ListingDetail`/`EventDetail` accept optional `prevItem`/`nextItem` props (`{ href: string; label: string } | null`), rendered as a `‹`/`›` (`lucide-react` `ChevronLeft`/`ChevronRight`) link pair with the adjacent item's name, directly under the "← Zurück zur Liste" link and above the rest of the detail content. Each page.tsx computes these from the same ordered array it already renders as the results list — `/projekte/page.tsx` uses `sortedListings` (so prev/next follows whatever `sortierung` is active — Neueste/Entfernung/Name/Kosten), `/termine/page.tsx` uses `events` (chronological) — via `selectedIndex = <array>.findIndex((x) => x.id === selectedId)`, then `<array>[selectedIndex - 1]`/`[selectedIndex + 1]` (`null` at either end of the array, or when there's no selection at all). The hrefs are built the same way every other result link is (`buildProjekteHref`/`buildTermineHref` with the target id, clearing the transient flash param), so stepping prev/next preserves the active filters/map position exactly like clicking a result from the list does. The wrapping `flex items-center justify-between` row carries `pr-[50px]` in both components so the right-aligned "weiter" link never sits under the fixed, `pointer-events-none` `DemoDataRibbon` in the top-right corner (see Pre-launch demo banner below) — that ribbon overlaps the top-right of the results column on the inline pane, which is exactly where this link renders.

## Results summary above `/projekte` and `/termine`'s result lists

Both `/projekte/page.tsx` and `/termine/page.tsx` build a one-line summary above their results (`resultsSummary`, e.g. `"12 Termine gefunden für Art „Workshop", Zielgruppe „Familien mit Kindern""`) from whichever filters are actually active — resolved to their human-readable option names/labels, not raw ids/params — so the count has visible context for how it was produced. Only present filters are listed; `/termine`'s default "upcoming only" Zeitraum (no explicit `von`) isn't treated as an active filter. `/projekte`'s version additionally walks every active `advancedGroups` entry (not just Projekt Typ/Kategorie), since listings can have several attribute-group filters active at once, each rendered as its own `"{Gruppenname} „{Optionen}""` segment. This summary/list is only shown when no `?projekt=<id>`/`?termin=<id>` detail is open (see master-detail above).

`location-radius-picker.tsx`'s `RADIUS_STEPS` (used by both `/projekte` and `/termine`) go up to `[1, 5, 10, 20, 50, 75, 100, 150, 200, 300, null]` (`null` = "Alle").

Each result card's thumbnail (`/projekte/page.tsx` and `/termine/page.tsx`) is flush against the card's top/left/bottom edges rather than sitting as a small square inside the card's own padding: the outer `<Link>` drops its own padding (`overflow-hidden rounded-2xl`, no `p-*`) and instead wraps the text content in an inner `flex-1 p-4 sm:p-6` div, while the `<img>` itself is `aspect-[4/3] w-52 sm:w-60 shrink-0 self-start rounded-l-2xl object-cover` — rounded only on the left (matching the card's own corners) since its right edge is an interior boundary against the text, not a card corner. The image is sized by a **fixed width with the height derived from `aspect-[4/3]`**, not the reverse (a stretched `h-full` with width derived from an aspect-ratio) — the latter was tried first and is a trap: a flex/grid item whose cross-size comes from `align-items: stretch` (matching the card's own content-driven height) while its main-size is simultaneously meant to come from `aspect-ratio` creates a circular sizing dependency that at least Chromium resolves by inflating the row's own height far beyond what the text content needs, which then inflates the image further — not just a proportion mismatch but a runaway feedback loop. Fixing the width and letting only the height be `auto` (derived from the aspect ratio) has no such loop and is exact every time; the `self-start` keeps the now-shorter-than-the-card image anchored to the top-left instead of being stretched by the row's default `align-items: stretch`. The tradeoff is that unusually tall cards (e.g. several wrapped attribute badges) leave a sliver of plain card background below the image instead of the image reaching the bottom edge — acceptable since the aspect ratio (not full-height coverage) is the actual requirement.

## Reorderable photo galleries (`/projekte/[id]/bearbeiten`, event edit)

`src/components/reorderable-photo-gallery.tsx` (`ReorderablePhotoGallery`, client component) replaces the former static photo grid in both edit forms' "Fotos" sections. Tiles are reorderable two ways: native HTML5 `draggable` (desktop mouse) and ←/→ buttons (touch/keyboard, since HTML5 drag-and-drop barely works on touchscreens) — both call the same `reorderAction(orderedIds)` prop, a Server Action **called directly from client code** (not through a `<form>`) and parameterized via `.bind(null, listingId)`/`.bind(null, eventId)` at the call site (`reorderListingMedia`/`reorderEventMedia` in `media-actions.ts`/`event-media-actions.ts`) — `.bind()` on a Server Action produces another valid Server Action reference, which is how a Client Component can receive one pre-parameterized without a server component passing a plain (non-serializable) closure. Both reorder actions re-verify ownership, then reject the whole payload unless it's exactly a permutation of the existing media ids (no partial/tampered application) before persisting new `position` values in a `$transaction`. Position 0 is always the thumbnail shown on `/projekte`/`/termine`, hence the "Vorschau" badge on the first tile and the hint text above the grid.

## 360°-Panoramabilder (`Media.isPanorama`)

`Media.isPanorama` (nullable-free `Boolean @default(false)`) flags a single photo as an equirectangular 360° panorama, uploaded through a **dedicated single-file upload path** separate from the regular multi-file "Fotos" form — a new "360°-Bild" section right below it in both edit pages (`/projekte/[id]/bearbeiten`, event edit), each with its own `<form>` (`uploadListingPanorama`/`uploadEventPanorama` in `media-actions.ts`/`event-media-actions.ts`, mirroring the existing `uploadListingMedia`/`uploadEventMedia` pattern but for exactly one file, no `multiple`).

- **Aspect-ratio validation** (`src/lib/media.ts`'s `isPanoramaAspectRatio(file)`): reads the file's dimensions via `sharp(...).metadata()` and requires the width/height ratio within ±0.05 of exactly 2 (roughly 1.95–2.05) — the standard equirectangular format. Rejected outright (`?error=panorama-format`) rather than silently accepting a merely-widescreen photo; both upload actions run this check before calling the same `processAndStoreImage()` every other photo goes through (a uniform-width resize preserves the aspect ratio exactly, so the stored display/thumbnail images stay 2:1 too — verified directly: a 2000×1000 source produced a 1600×800 display image).
- **Size limit**: `MAX_PANORAMA_SIZE` (12MB) in `src/lib/media.ts` — a dedicated, higher limit than `MAX_IMAGE_SIZE` (8MB, regular photos), since equirectangular panoramas are typically higher-resolution than a normal gallery photo. Rejected with `?error=panorama-toobig` (a distinct error code from the generic photo-upload `?error=toobig`, so the banner can state the correct 12MB figure).
- **Gallery highlight**: `PhotoGallery` (grid + lightbox) and `ReorderablePhotoGallery` (edit-form grid) both render a small "360°" pill badge (`RotateCw` icon from lucide-react + text, bottom-left corner of the tile — top-left is already used by `ReorderablePhotoGallery`'s "Vorschau" badge) on any tile where `isPanorama` is true, so panorama photos are visually distinguishable from regular ones without leaving the normal grid.
- **Interactive viewer in the lightbox**: opening a panorama-flagged tile in `PhotoGallery`'s full-screen popup renders `src/components/panorama-viewer.tsx` (`PanoramaViewer`, `mode="interactive"`) instead of a plain `<img>` — full drag-to-look-around, zoom, and the library's own navbar controls.
- **Ambient auto-rotating preview on the detail page**: `listing-detail.tsx`/`event-detail.tsx` each look up the first `isPanorama` photo (`listing.media.find((m) => m.isPanorama)`) and, if one exists, render the *same* `PanoramaViewer` component in `mode="ambient"` directly above the regular `PhotoGallery` — a compact (`h-64`/`h-80`), rounded, no-navbar "hero" widget that starts auto-rotating immediately at a slow, subtle speed (the `@photo-sphere-viewer/autorotate-plugin`, `autorotateSpeed: "0.5rpm"`, `autostartDelay: 0`) rather than requiring interaction; manual drag still works and rotation resumes after the user goes idle (the plugin's own default). This is a deliberately different, lighter-weight rendering of the *same photo* than the lightbox's fully-interactive view — the panorama still also appears normally (badged) in the gallery grid below it.
- **`@photo-sphere-viewer/core` + `@photo-sphere-viewer/autorotate-plugin`** (new dependencies) are loaded the same way the app's Leaflet maps are: a dynamic `import(...)` inside a mount `useEffect` (the library is WebGL/canvas-based and touches `window` at module load, so it can't be a top-level import in code that might render on the server), while `@photo-sphere-viewer/core/index.css` is a plain top-level import — Next.js's bundler handles a third-party CSS import specially regardless of SSR, the same way `leaflet/dist/leaflet.css` is imported in `address-fields.tsx`.

## Videos in der Galerie (`Media.type === "VIDEO"`)

Videos (up to 200MB each) can be uploaded into the same gallery as photos, via a dedicated "Videos" section below the existing "Fotos"/"360°-Bild" sections in both edit pages, rendered by `src/components/video-upload-form.tsx` (`VideoUploadForm`, one client component shared by both `/projekte/[id]/bearbeiten` and the event edit page, parameterized by an `endpoint` prop).

- **Deliberately not a Server Action, unlike every other upload in this app** (see the Pages convention above). A real upload-progress bar needs `XMLHttpRequest.upload.onprogress`; a Server Action invoked directly from client code instead goes through Next's own fetch-based RSC protocol, which doesn't expose upload progress at all. So video upload is a plain Route Handler — `src/app/api/projekte/[id]/videos/route.ts` (listings) and `src/app/api/projekte/[id]/termine/[eventId]/videos/route.ts` (events), each duplicating the same inline ownership check the corresponding `*-media-actions.ts` file uses for photos/panoramas — POSTed to directly via `XMLHttpRequest` from `VideoUploadForm`. This also sidesteps `experimental.serverActions.bodySizeLimit` in `next.config.ts` entirely: Route Handlers aren't subject to it, so that setting stays at its original `"50mb"` (sized for photo uploads only) rather than needing to account for a 200MB video.
- **Client-side poster-frame thumbnail, no ffmpeg dependency.** `VideoUploadForm`'s `extractVideoThumbnail(file)` grabs a real preview frame entirely in the browser: a hidden `<video>` element loads the file (`URL.createObjectURL`), seeks to `min(1s, duration/2)`, and the `seeked` frame is drawn onto a `<canvas>` (scaled to max 400px wide, matching `THUMBNAIL_MAX_WIDTH` for photos) and read back via `canvas.toBlob(..., "image/jpeg", 0.8)`. This avoids adding `ffmpeg` as a system dependency just to extract a poster frame server-side. Capture failure (unsupported codec, a `loadedmetadata`/`seeked` event that never fires — guarded by an 8s timeout) resolves to `null` rather than throwing, so the video still uploads without a thumbnail rather than failing the whole upload.
- **Upload payload pairing**: for `n` selected files, the client builds one `FormData` with `count=n` plus, per file `i`, a `video_${i}` field (the video) and an optional `thumbnail_${i}` field (the JPEG blob, only present if extraction succeeded) — indexed fields rather than two parallel `getAll()` arrays, so a failed thumbnail for one file can never shift the pairing for the files after it. The route loops `i` from `0` to `count`, validating each `video_${i}` against `isAllowedVideoType()`/`MAX_VIDEO_SIZE` (skipping — not failing the whole request — invalid ones) and passing the matching `thumbnail_${i}` into `storeVideo(file, keyPrefix, thumbnail)`, which now stores both the video and (if given, and under a 2MB sanity cap — `MAX_VIDEO_THUMBNAIL_SIZE` in `src/lib/media.ts`) the thumbnail as the `Media` row's `thumbnailKey`, exactly like a photo's thumbnail. A video with no usable thumbnail keeps `thumbnailKey: null`; `deleteListingMedia`/`deleteEventMedia` already handle this correctly unmodified, since both already guard `thumbnailKey` deletion with `if (media.thumbnailKey)`.
- **Gallery rendering** (`photo-gallery.tsx`'s `GalleryTileMedia`, and inline in `reorderable-photo-gallery.tsx`): a video tile with a `thumbnailKey` renders that image with a centered `PlayCircle` "play button" overlay (`VideoPlayBadge`) — the same visual language as a YouTube thumbnail — so it reads as "this plays" without needing a full placeholder tile. Only a video with no thumbnail (capture failed, or predates this feature) falls back to the plain `VideoTile` placeholder (icon + "Video" label on a neutral background).
- **Streaming + HTTP Range support in the media proxy** (`src/app/api/media/[...path]/route.ts`) — necessary for `<video>` seeking/scrubbing at this file size, and to avoid buffering a 200MB file into memory per request. The route always streams via `minioClient.getObject`/`getPartialObject` (`getObjectStream()` in `src/lib/storage.ts`, which replaced the old `getObjectBuffer()` full-buffer read) and converts the Node `Readable` to a web `ReadableStream` (`Readable.toWeb`, `node:stream`) for the `NextResponse` body. A `Range: bytes=start-end` request header is parsed and answered with `206 Partial Content` + `Content-Range`/`Content-Length`; a request with no `Range` header gets the whole object with `200 OK` and `Accept-Ranges: bytes` so the browser knows it's allowed to request ranges on a later seek.
- **Progress bar + inline result, no redirect/query params.** Unlike every other upload form in this app, `VideoUploadForm` doesn't redirect back to a `?fotos=1`/`?error=...` URL — it renders its own status inline (a "Video(s) werden vorbereitet…" message while extracting thumbnails, then a percentage progress bar driven by `xhr.upload.onprogress` while the request is in flight, then a success/error message from the route's JSON response) and calls `router.refresh()` on success to pull the new `Media` rows into the already-rendered page.

### Video-Links (YouTube/Vimeo/andere) statt Datei-Upload (`Media.isVideoLink`)

Below the file-upload "Videos" section, both edit pages also have a plain `<form>` (`addListingVideoLink`/`addEventVideoLink` in `media-actions.ts`/`event-media-actions.ts`, back to the normal Server Action + `?fotos=1`/`?error=videolink-ungueltig` redirect convention — no progress bar needed for a URL) to add a video by external link instead of uploading a file.

- **Schema**: `Media.isVideoLink Boolean @default(false)` — the row's `type` stays `"VIDEO"` either way (same gallery tile/badge treatment as an uploaded video), this flag only changes what `storageKey` holds and how playback works. For an `isVideoLink` row, `storageKey` is **not** a MinIO key — it's the embeddable player URL itself (see below), and is never passed through `/api/media`. `deleteListingMedia`/`deleteEventMedia` both skip `deleteObject(media.storageKey)` when `isVideoLink` is true (it isn't a real object to delete) but still delete `thumbnailKey` when present, since that one *is* a real MinIO object.
- **URL handling** (`src/lib/video-link.ts`): `normalizeVideoLinkUrl()` reuses `normalizeHomepageUrl()` (same scheme validation — rejects `javascript:`/`data:`/etc., auto-prepends `https://`) since a video link has identical input-safety needs to the homepage-URL field, **plus rejects a URL whose hostname is this site's own domain or any subdomain of it** (compared against `SITE_URL`'s hostname) — there's no legitimate reason a "video link" would point back at ligem.de itself, and doing so would matter for the sandbox-escape reason below. `toEmbeddableUrl()` rewrites a normal YouTube (`youtube.com/watch?v=`, `youtu.be/`, `/shorts/`) or Vimeo (`vimeo.com/<id>`) URL into its actual embeddable form (`https://www.youtube.com/embed/<id>` / `https://player.vimeo.com/video/<id>`) — required specifically for those two, since their normal pages refuse to be framed at all. **Any other provider's URL is returned unchanged and embedded directly as-is** — a deliberate product decision (not restricted to a trusted-provider allowlist) made explicitly aware of the tradeoff: framing an arbitrary third-party page carries real tracking/clickjacking risk that a safer allowlist-based design would avoid. The lightbox's `<iframe>` (`photo-gallery.tsx`) sets `sandbox="allow-scripts allow-presentation allow-popups"` as partial mitigation — **deliberately without `allow-same-origin`**: that combination with `allow-scripts` is a well-known sandbox-escape (a framed page that turns out to share the parent's origin gets real same-origin DOM access once it also has script rights, defeating the sandbox), which is exactly why a same-origin URL is rejected at the source too — belt and suspenders, not either one alone. `referrerPolicy` is `"strict-origin-when-cross-origin"` (sends only the page's origin, not its full path, to the framed site) rather than `"no-referrer"` — a fully stripped referrer was tried first and broke YouTube playback outright (its player validates the embedding origin via the referrer for many videos; with none at all it fails with "Fehler bei der Konfiguration des Videoplayers" / error 153), so this is the more restrictive policy that still keeps YouTube's own embed validation working.
- **Best-effort thumbnail** (`fetchVideoLinkThumbnail()`, via the same SSRF-safe `fetchPublicBuffer`/`fetchPublicText` helpers the homepage-import feature already uses): YouTube's thumbnail URL is deterministic from the video id (`img.youtube.com/vi/<id>/hqdefault.jpg`, no extra request needed before downloading it); Vimeo needs one oEmbed JSON call first (`vimeo.com/api/oembed.json?url=...`) to learn its `thumbnail_url`. Any other provider gets no auto-thumbnail — the gallery falls back to its plain placeholder tile, exactly like an uploaded video whose client-side frame capture failed. The downloaded image is resized/stored via `storeThumbnailOnly()` (`src/lib/media.ts`) — the same 400px-wide JPEG treatment as every other thumbnail, just with no accompanying "original" to store alongside it (there isn't one; the video itself lives on the external provider's site).
- **Lightbox playback branches three ways** now: `type === "VIDEO" && isVideoLink` → `<iframe src={storageKey}>`; `type === "VIDEO" && !isVideoLink` → local `<video src={/api/media/storageKey}>`; anything else → the existing photo/panorama branches.
- **Lightbox playback**: `PhotoGallery`'s full-screen popup renders a plain `<video controls>` (no autoplay — browsers block unmuted autoplay anyway, and a user-uploaded video has no reliable "safe to autoplay" signal) instead of an `<img>`/`PanoramaViewer` when the selected item's `type === "VIDEO"`, wrapped in the same `onClick={(e) => e.stopPropagation()}` guard the panorama viewer and plain `<img>` already use (so operating the native video controls doesn't bubble a click up to the backdrop and close the lightbox) — always plays the original video (`storageKey`), never the thumbnail.

## Rich-text fields (`howWeLive`, `whoWeAreLooking`, event `description`)

These three fields are stored as **sanitized HTML**, not plain text, edited via `src/components/rich-text-field.tsx` (`RichTextField`, client component) — a deliberately reduced Tiptap editor (bold, italic, underline, headings H2/H3, blockquote, bullet/numbered list; no tables/images/links/colors/code) with a small toolbar, dropping into the existing plain `<form action={serverAction}>` convention exactly like the `<textarea>` it replaces: it syncs `editor.getHTML()` into a hidden `<input type="hidden" name={name}>` on every change (empty doc → `""`, not Tiptap's own `"<p></p>"`), so the server action still just reads `formData.get(name)` and gets HTML back instead of plain text. Every extension the toolbar exposes (`heading`, `blockquote`, `underline`) is already bundled in Tiptap v3's `StarterKit` — enabling them was just flipping their `configure()` flags from `false` to an options object (`heading: { levels: [2, 3] }` to cap the levels, `blockquote: {}`/`underline: {}` for the rest) rather than adding new packages. `src/lib/sanitize-html.ts`'s `ALLOWED_TAGS` must stay in sync with whatever the toolbar can produce — it now also allows `u`, `h2`, `h3`, `blockquote` alongside the original `p`/`strong`/`em`/`ul`/`ol`/`li`/`br`, still with `ALLOWED_ATTR: []` (no attributes on any tag, so there's no id/class/style injection surface even via these tags).
- **Toolbar buttons need `onMouseDown={(e) => e.preventDefault()}`** — without it, mousedown on the button shifts focus away from the editor and collapses whatever text was just selected *before* the `onClick` handler's `chain().focus().toggleBold().run()` even runs, so Bold/Italic silently apply to an empty selection instead of the highlighted text. This is a general contentEditable-toolbar pitfall, not Tiptap-specific.
- `useEditor` is called with `immediatelyRender: false` (a Next.js/SSR-specific Tiptap option) to avoid a hydration mismatch, since the editor's initial content would otherwise render differently on the server vs. the client's first paint.
- `src/lib/sanitize-html.ts` exports `sanitizeRichText(value)` (DOMPurify, `isomorphic-dompurify`, allowlisting exactly the tags the toolbar can produce: `p`, `strong`, `em`, `u`, `h2`, `h3`, `blockquote`, `ul`, `ol`, `li`, `br`, with `ALLOWED_ATTR: []` — nothing else, and no attributes on anything, survives regardless of what a client actually submits, since the editor's own UI restrictions aren't a security boundary by themselves) and `stripHtml(html, maxLength)` (plain-text excerpt for contexts that need a string, not markup: `<meta name="description">`, Open Graph descriptions, JSON-LD `description` fields — strips tags rather than rendering them, so a description never gets cut off mid-tag). All four server actions that persist these fields (`createListing`/`updateListing` in their respective `actions.ts`, `createEvent`/`updateEvent` in `/projekte/[id]/termine/actions.ts`) call `sanitizeRichText()` instead of the plain-text `optionalString()` helper used for other fields; `listing-detail.tsx`/`event-detail.tsx` render the sanitized HTML via `dangerouslySetInnerHTML` (safe specifically because it's sanitized at write time) with a small arbitrary-variant class (`[&_ul]:list-disc [&_ul]:pl-5 [&_ol]:list-decimal [&_ol]:pl-5 [&_h2]:text-lg [&_h2]:font-bold [&_h3]:font-semibold [&_blockquote]:border-l-4 [&_blockquote]:border-text/20 [&_blockquote]:pl-4 [&_blockquote]:italic [&>*+*]:mt-3`) for basic heading/quote/list/paragraph styling, since Tailwind has no utility classes reaching into unstyled rendered markup like this.
- The demo generator produces HTML for these same three fields too (see "Demo data generators" above) — matching the real editor's tag allowlist, since a generated listing/event should look exactly like a real submission would.

## SEO & KI-Agenten-Optimierung

`src/lib/site.ts` exports the single shared `SITE_URL` constant (`https://ligem.de`) used by every SEO-related file below — `metadataBase`, canonical URLs, sitemap/robots entries, and JSON-LD `url` fields all read from it, so a real domain change only touches one file.

- `src/app/robots.ts` / `src/app/sitemap.ts` (Next.js's `MetadataRoute.Robots`/`MetadataRoute.Sitemap` file conventions, auto-served at `/robots.txt`/`/sitemap.xml`) — a single catch-all rule allows every crawler including AI bots (GPTBot, CCBot, Google-Extended, PerplexityBot, ClaudeBot, ...) with no exceptions, a deliberate choice to maximize visibility in AI answer engines alongside classic search; only genuinely private/owner-only paths (`/admin`, `/api/`, `/meine-projekte`, edit/management forms) are disallowed. **The sitemap excludes `isDemo: true` listings (and their events)** — the synthetic demo dataset (see Demo data generators) must never be indexed as if it were real communities/events; `prisma.event.findMany`'s `OR: [{ listingId: null }, { listing: { isDemo: false } }]` keeps organization-only events (no listing at all) while still excluding events attached to a demo listing.
- `public/llms.txt` — a short, hand-written Markdown overview (per the emerging llms.txt convention) for AI agents/crawlers: what LiGem is, its four audiences, core page links, and a pointer to `sitemap.xml` for the full, dynamic listing/event catalog. Deliberately doesn't try to embed the dynamic dataset itself — that's what the sitemap is for.
- `public/og-default.jpg` (1200×630) — generic Open Graph preview image for pages without their own photo, generated once via `sharp` compositing `logo.png` onto the `--color-bg` background (same one-off-script approach as the homepage's zielgruppen photos), not a runtime-rendered image.
- `src/components/json-ld.tsx` (`JsonLd`) — renders a `<script type="application/ld+json">` from a plain object; used both site-wide (root `layout.tsx`: `Organization` + `WebSite`) and per-content-type.
- **Dynamic metadata + JSON-LD only exists for the two content types that actually have individual public pages**: `/projekte/[id]/page.tsx` and `/termine/[eventId]/page.tsx` each export `generateMetadata` (title, description, canonical, Open Graph image from the first photo, `robots: {index: status === "PUBLISHED"}`) built on a `cache()`-wrapped Prisma query shared with the page body itself (React's `cache()` dedupes the identical `findUnique` call within one request — otherwise `generateMetadata` and the page component would each hit the database separately for the same row). The actual JSON-LD is rendered **inside the shared `listing-detail.tsx`/`event-detail.tsx` components** (not the page files) — since both are also used for the `?projekt=`/`?termin=` inline preview pane (see master-detail above), this means both the standalone page and the inline pane get correct structured data for free, without duplicating the JSON-LD-building logic in both places. Listings use a generic `Organization` (schema.org has no clean single type for "a group of people looking for/presenting a shared home" — `Organization` is the least-misleading fit and still helps AI-agent entity understanding, which matters more here than Google rich-result eligibility); events use `Event` (a correct, rich-result-eligible fit: `startDate`/`endDate`, `location` with `PostalAddress`/`GeoCoordinates`, `organizer`, `isAccessibleForFree`/`offers`). Both also render a `BreadcrumbList`. Structured data is only emitted when `status === "PUBLISHED"` — a pending/rejected/archived draft has no business being described to search engines or AI agents as a real, existing community/event.
- `/projekte/page.tsx` and `/termine/page.tsx` also export `generateMetadata`, reading `searchParams` the same way the page body does, with two cases: no `projekt`/`termin` selection → indexable, self-canonical **stripped of all query params** (`/projekte`/`/termine` bare) regardless of which filters are active, since indexing every filter-parameter permutation as separate pages would be duplicate-content noise; a `projekt`/`termin` selection active → `robots: {index: false, follow: true}` with the canonical pointing at the corresponding standalone `/projekte/<id>`/`/termine/<id>` page instead, since the inline pane duplicates that page's content under a different URL.
- Every other `page.tsx` gets a plain static `metadata` export: genuinely public content (`/hilfe` + its five subpages, `/registrieren`, `/anmelden`) gets a real title/description; purely private or functional pages (`/meine-projekte`, all of `/admin/**`, `/projekte/neu`, `/projekte/[id]/bearbeiten`, `/projekte/[id]/termine/**`, `/termine/neu`) get a title (for the browser tab) plus `robots: {index: false, follow: false}` — belt-and-suspenders alongside the `robots.txt` disallow above, since a crawler that ignores the disallow would still see the per-page noindex.
- Root `layout.tsx` sets `metadataBase`, a site-wide `title.template` (`"%s - LiGem"`, matching the existing `"<Seite> - LiGem"` convention already used by the legal pages), and Open Graph/Twitter defaults; `{children}` is wrapped in `<main>` rather than a plain `<div>` for landmark semantics.

## Zugriffs-Statistik (`ListingView` / `EventView` / `PageView`)

Every listing and event gets a view-count statistics feature, reachable from `/meine-projekte` (listings) and `/projekte/[id]/termine` (that listing's events) for owners/co-managers, and additionally from a site-wide dashboard under `/admin/statistik` (ADMIN only) that also covers every other page on the site at a less detailed level.

### Schema and recording

- **Three parallel models**, one per content scope, all the same shape: `ListingView`, `EventView` (mirrors `ListingView` exactly, minus `searchTerm` — see below), and `PageView` (the generic site-wide tracker, see "Site-wide tracking" below — no `viewType` or search/filter fields, since those concepts don't apply to a generic page). Kept as three separate models rather than one polymorphic table, matching this app's existing convention of parallel-but-separate Listing/Event infrastructure (`ListingAttributeOption`/`EventAttributeOption`, etc.) — a single table would need two nullable FK columns (`Media`'s pattern) plus `WHERE ... IS NULL` noise on every aggregation query, for no real benefit here.
- Every row carries: `viewType: OVERVIEW | DETAIL` (Listing/Event only), `viewedAt`, `viewerId?` + `viewer` relation, `isBot`/`botName?` (see bot detection below), `referrerHost?` (hostname only from the `Referer` header, never the full URL — could carry another site's own path/query details that aren't this app's to keep), and — per explicit product decision — **`hostname?`/`country?` derived from the viewer's IP, but never the raw IP itself** (see "IP-derived hostname/country" below). `ListingView` additionally has `searchTerm?` (the active `suche` keyword, lowercased so casing doesn't fragment aggregation) and `filtersSummary?` (a human-readable summary of every other active filter); `EventView` has `filtersSummary?` only, since `/termine` has no keyword-search field. This still isn't nothing from a DSGVO standpoint — flag it for `/datenschutz`'s eventual legal review alongside everything else already listed there.
- **`OVERVIEW`**: recorded once per listing/event whenever it's actually rendered as a card in `/projekte`'s/`/termine`'s results list — an impression, not a click — **only when that results list is actually shown** (i.e. no `?projekt=`/`?termin=` selection active), since the inline detail pane replaces the results list entirely (see master-detail above) and a card that isn't on screen must not get an impression.
- **`DETAIL`**: recorded once whenever a listing's/event's full detail is actually opened — either the standalone `/projekte/[id]`/`/termine/[eventId]` page (only when `status === "PUBLISHED"`, so an owner/admin previewing a pending/rejected/archived item for moderation doesn't count as a "view") or the inline `?projekt=<id>`/`?termin=<id>` pane (never both `OVERVIEW` and `DETAIL` for the same render).
- **`searchTerm`/`filtersSummary` reuse the exact `suche`/`activeFilters` values `/projekte/page.tsx`/`/termine/page.tsx` already compute for their own "N Projekte/Termine gefunden für ..." results heading** — passed into `recordListingViews`/`recordEventViews` as a `searchContext` argument (Listing) or a plain `filtersSummary` string (Event) right after that heading's own computation (moved the recording call to after that point in `/projekte/page.tsx`, since it originally ran earlier, before `activeFilters` existed yet). Only set for a view recorded while that search/filter form actually produced this result (OVERVIEW, or the DETAIL reached via the inline pane from that same search) — a standalone detail-page visit has no search context, so both stay null there.
- **Recording helpers** (`src/lib/listing-views.ts`'s `recordListingViews(listingIds, viewType, searchContext?)`, `src/lib/event-views.ts`'s `recordEventViews(eventIds, viewType, filtersSummary?)`) — the actual `createMany` write (plus the slow IP-derived lookups, see below) is deferred via `after()` (same mechanism the demo-data generator uses, see Demo data generators) so a page's render latency never waits on it — but `headers()`/`auth()` are read **before** scheduling `after()`, not inside it, since Next.js explicitly rejects calling request-scoped APIs like `headers()` from inside an `after()` callback ("used headers() inside after(). This is not supported" — verified directly: calling it inside the callback silently failed every write in dev testing until moved outside). Callers `await recordListingViews(...)`/`await recordEventViews(...)` so that outer read (cheap) still happens while the request is active. Wrapped in try/catch — a failed write must never break the page it was recording a view for.

### Bot detection

`src/lib/bot-detect.ts`'s `detectBot(userAgent)`: a User-Agent substring match against known search engines and AI/web agents (Googlebot, Bingbot, GPTBot, ClaudeBot, PerplexityBot, CCBot, Applebot, social-platform link-preview bots, SEO crawlers, ...) — the same crawlers this app's `robots.txt` deliberately welcomes (see SEO section) — plus a generic `bot|spider|crawler|slurp` fallback for anything else that self-identifies as automated but isn't specifically named. Order matters in the pattern list: more specific patterns (`Google-Extended`) must come before broader ones that would also match their substring.

### IP-derived hostname/country

Per explicit product decision, the statistics feature also shows each view's reverse-DNS hostname and GeoIP country — **without ever persisting the raw IP address itself**, only these two derived, less-identifying summaries (`src/lib/ip-lookup.ts`):

- **`getClientIp(headers)`** reads the reverse proxy's `X-Forwarded-For` (first entry) with an `X-Real-IP` fallback — requires the proxy to actually set one of these (mod_proxy does by default, see DEPLOYMENT.md's Apache section); returns `null` in local dev without a proxy in front of the app.
- **`reverseDnsLookup(ip)`** wraps Node's `dns.promises.reverse()` with a 2s timeout (most IPs have no PTR record at all — best effort, never throws).
- **`countryForIp(ip)`** uses **`geoip-lite`** (new dependency, bundles its own local IP→country database, no outbound network call — the visitor's IP never leaves this server just to answer "which country", unlike a public geolocation API).
- **`lookupIpInfo(ip)`** combines both, called from inside `after()` in the recording helpers (both listing/event and generic PageView, see below) — it's genuinely slow (DNS + a data lookup) and must never block a page response.
- **`geoip-lite` needed `serverExternalPackages: ["geoip-lite"]` in `next.config.ts`**: it loads its bundled `.dat` database via a runtime `path.join(__dirname, ...)`, which Turbopack's bundler rewrites into its own virtual `/ROOT/...` module namespace — breaking the lookup with `ENOENT ... geoip-country.dat` from *any* bundled context (verified directly: reproduced from both a plain Route Handler and Middleware/Proxy, not middleware-specific). `serverExternalPackages` makes Next.js load it via a plain, unbundled `require()` at its real on-disk location instead, which fixed it immediately.
- Country codes are rendered as localized names via `new Intl.DisplayNames(["de"], { type: "region" })` (e.g. "DE" → "Deutschland") — no extra dependency needed for that part.

### Site-wide tracking (`PageView`, `src/proxy.ts`)

Every route **except** `/projekte*`/`/termine*` (already covered in full detail above, would double-count) gets a generic page-view row via `src/proxy.ts` — Next.js's file-convention replacement for the older `middleware.ts` name (Next 16 deprecated "middleware" in favor of "proxy": same file shape, same `matcher` config export, just the exported function renamed from `middleware` to `proxy`; see https://nextjs.org/docs/messages/middleware-to-proxy). This is the only place in the App Router that sees every request without individually instrumenting every single `page.tsx`.

- **`matcher`** excludes `_next/static`, `_next/image`, `favicon.ico`, `robots.txt`, `sitemap.xml`, `api/*`, and `projekte`/`termine` (the content-specific exclusion above).
- **Skips Next.js's own link-prefetch requests** (`request.headers.get("next-router-prefetch")`) — the App Router's client-side `<Link>` prefetches routes in the background before they're actually visited (any link scrolled into view), which would otherwise wildly inflate counts for anything linked from a high-traffic page.
- **Does not do the actual bot-detection/GeoIP/DB-write work itself** — since `geoip-lite` needed `serverExternalPackages` just to work from a *regular* Route Handler (see above), doing it inline in the Proxy (an even more restricted bundling context) wasn't attempted further; instead, `proxy.ts` just relays the request's own headers (User-Agent, Referer, X-Forwarded-For, X-Real-IP, and — importantly — the session cookie, so the internal endpoint's own `auth()` call still sees who's logged in) via an internal `fetch()` (wrapped in `after()`) to a plain Route Handler, **`/api/internal/page-view/route.ts`**, which does everything else exactly like `recordListingViews`/`recordEventViews` already do (same bot detection, same `lookupIpInfo`, same DB write) — that handler runs in the regular server runtime, unaffected by the bundling issue.

### Statistics pages

- **`/projekte/[id]/statistik`** (owner/co-manager via `canManageListing` — which already includes an ADMIN bypass, so this one check alone covers "Eigentümer und Administrator" — or 404): top-line `OVERVIEW`/`DETAIL` totals, a `ViewTimelineChart` ("Zugriffe der letzten 30 Tage" — see below), the "Woher kamen die Zugriffe?" bot/user/referrer breakdown, separate "Herkunftsländer"/"Hostnamen" breakdowns, and — only for listings — "Meistgesuchte Suchbegriffe"/"Meistgenutzte Filterkombinationen". `/meine-projekte` shows a compact per-listing summary (two icon+count pairs) plus a "Statistik ansehen" link to this page, computed via one batched `groupBy(["listingId", "viewType"])` across every listing shown rather than a query per card.
- **`/projekte/[id]/termine/[eventId]/statistik`** (owner/co-manager via `canManageEvent`, same ADMIN-bypass logic, or 404) — the Event equivalent of the page above, minus the search-terms section. `/projekte/[id]/termine` ("Termine verwalten") shows the same compact per-event summary + "Statistik" link, next to the existing Anmeldungen/Bearbeiten/Löschen actions.
- **`/admin/statistik`** (ADMIN only, linked from `/admin`) is the one page that spans **all three** scopes in one place: an overall "Zugriffe auf alle Seiten" total (Projekte + Termine + Sonstige Seiten combined) at the top, then a full detailed **Projekte** section (identical shape to the per-listing page: totals, timeline, "Meistgesehene Projekte" leaderboard linking to each listing's own `/statistik`, source/geo/search-term/filter breakdowns), a full detailed **Termine** section (same, minus search terms; its "Meistgesehene Termine" leaderboard links to the nested `/projekte/[id]/termine/[eventId]/statistik` route, resolved via each event's own `listingId`), and a deliberately **less detailed "Sonstige Seiten"** section per explicit product decision (every other route on the site — total + a "Meistbesuchte Seiten" top-20 leaderboard by raw path + the bot/user/referrer breakdown, but no timeline graph, no geo breakdown, and no per-page drill-down page) — any admin can also reach an individual listing's/event's full detail page regardless of ownership via the same `canManageListing`/`canManageEvent` bypass.

### Shared aggregation and display code

- **`src/lib/view-stats.ts`** (renamed from the Listing-only `listing-view-stats.ts`) holds three parallel families of aggregation functions — `getListingView*`, `getEventView*`, and `getPageViewStats` — each parameterized by that model's own `Prisma.*WhereInput` (`{ listingId }`/`{ eventId }` for one item, `{}` for site-wide) so the exact same logic produces either scope:
  - `get*ViewTypeCounts(where)` — the two top-line totals.
  - `get*ViewsOverTime(where, days=30)` — fetches `{viewedAt, viewType}` for the last N days and buckets them per-day in JS (`bucketByDayAndType`) rather than a SQL date-truncating `groupBy` (Prisma's `groupBy` can't truncate a `DateTime` to a day on its own), returning a zero-filled `DailyViewCounts[]` (every day in range present, even with 0 views) so the chart never has gaps.
  - `get*ViewSourceBreakdown(where)` — the bot/user/referrer breakdown; three separate `groupBy`s (bot names where `isBot`, viewer ids where not bot and `viewerId` set, referrer hosts for everything else) rather than one query, since those are three mutually-exclusive partitions of the table with different grouping keys; registered viewers' names are resolved via one follow-up `user.findMany({ where: { id: { in } } })`.
  - `get*GeoBreakdown(where)` — separate `country`/`hostname` `groupBy`s, kept apart from the source breakdown above since they answer a different question ("where geographically" vs. "who/via what").
  - `getListingSearchBreakdown(where)`/`getEventFilterBreakdown(where)` — `groupBy` on `searchTerm`/`filtersSummary` (`not: null`, `orderBy: {_count: {...: "desc"}}`, `take: 15`).
  - `getPageViewStats(where)` — the "Sonstige Seiten" shape: total, bot/user/referrer breakdown, and a top-20-paths `groupBy` on `path`.
- **`src/components/view-source-breakdown.tsx`**'s `ViewSourceBreakdown` is one shared leaderboard component reused for *every* breakdown above (bot/user/referrer, countries, hostnames, search terms, filter combinations) — plain CSS bars (no charting library) sized relative to the largest entry in **that specific list** (the percentage denominator is the sum of the passed-in `sources` themselves, not some other externally-tracked total, so calling it for, say, just the countries list produces correct percentages for that list alone). Icon-per-`kind` (`Bot`/`UserRound`/`Globe2`/`Flag`/`Server`/`Search`/`Filter`). **Named registered viewers only link to a profile for an admin viewer of the statistics page** (`viewerIsAdmin` prop) — the link target is `/admin/nutzer#user-<id>` (a plain anchor id added to each user's `<li>` on that existing admin-only page, not a new public profile page), which only an admin can actually reach; a plain owner sees the same name as inert text instead, since that destination would just 404 them via `requireAdminPage()`.
- **`src/components/view-timeline-chart.tsx`**'s `ViewTimelineChart` — a plain CSS stacked bar chart (no charting library), one bar per day split into an Übersicht segment (bottom) and a Detail segment (top), computed against a fixed pixel chart height (not nested percentage-of-percentage math, which gets confusing/fragile fast) — each bar's exact counts are in its native `title` tooltip, and only every ~Nth day gets a visible x-axis label to avoid clutter over a 30-day range.
- **`src/lib/referrer-label.ts`'s `labelForReferrerHost(host)`** turns a raw referrer hostname into a friendly label: known search engines/social/chat platforms get a real name (e.g. "Google-Suche", "DuckDuckGo", "ChatGPT"), this site's own hostname (or a subdomain of it) becomes "Innerhalb von LiGem", `null` becomes "Direktaufruf / unbekannt", anything else falls back to its raw hostname.

## Kontaktanfragen (`/projekte/[id]/anfragen`) & offene-Anfragen-Badge

Contact requests used to only ever land in the `ContactRequest` table (`submitContactRequest`, see above) with no notification and no owner-facing page at all — an owner had no way to know one had arrived short of querying the database directly. Now:

- **`/projekte/[id]/anfragen`** (owner/co-manager via `canManageListing`, or 404) lists every `ContactRequest` for that listing (newest first) — sender name/email (a `mailto:` link), message, timestamp, and a status pill (Offen/Angenommen/Abgelehnt). A `PENDING` request gets "Annehmen"/"Ablehnen" buttons (`src/app/projekte/[id]/anfragen/actions.ts`'s `acceptContactRequest`/`declineContactRequest`, both plain `status` updates after the same `requireListingAccess` check as every other per-listing action file) — accepting/declining doesn't (yet) notify the *sender* in any way; it exists to let the owner triage their inbox, matching literally what was asked for here. Linked from `ListingDetail`'s owner-controls row (next to "Projekt bearbeiten"/"Termine verwalten") and from `/meine-projekte`'s per-listing row (with a red pending-count badge, computed via one batched `contactRequest.groupBy(["listingId"])` across every listing shown, mirroring that page's existing view-count query).
- **Email forwarding, opt-in** (`User.notifyContactRequestsByEmail`, toggled via a checkbox in `/mein-konto`'s "Persönliche Daten" form, saved together with name/email through the same `updateProfile` action): when `submitContactRequest` creates a new `ContactRequest`, `notifyContactRequest()` (same file) looks up the listing's creator + every `ListingManager`, keeps only those with the flag set, dedupes by email (defensive — nothing stops the same user from ending up as both creator and a co-manager row), and fires one plain-text email per recipient with the sender's name/email/message and a link to `/projekte/[id]/anfragen`. The actual SMTP send is deferred via `after()` (same non-blocking pattern as `recordListingViews`).
- **`src/lib/mailer.ts`** wraps `nodemailer` — optional at the infra level like every other feature-gating env var in this app (`ANTHROPIC_API_KEY`, `NEXT_PUBLIC_MAPTILER_KEY`, ...): without `SMTP_HOST`/`SMTP_USER`/`SMTP_PASSWORD` set, `sendMail()` just logs a warning and returns instead of throwing, so nothing else in the app (including local dev) depends on real mail credentials existing. `SMTP_PORT` defaults to `587` (STARTTLS); `secure: true` (implicit TLS) only kicks in for port `465`. `SMTP_FROM` is optional and falls back to `SMTP_USER`. All five (`SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASSWORD`/`SMTP_FROM`) are wired into `docker-compose.yml`'s `web.environment` from the root `.env`, same passthrough pattern as everything else there.
- **Header nav notification badge** (`AccountMenu`'s small red circle next to the account-menu trigger, visible without opening the dropdown): shows `src/lib/open-requests.ts`'s `getOpenRequestsCount(userId)` — the combined count of `ContactRequest`s with `status: PENDING` across every listing this user owns/co-manages, plus `EventRegistration`s with `viewedAt: null` across every event they own/co-manage (directly, or via the event's listing). `EventRegistration` has no status/read concept of its own at all (see above) — `viewedAt` exists purely to give this badge something to count for Termine, mirroring `ContactRequest.status` for the same purpose; visiting `/projekte/[id]/termine/[eventId]/anmeldungen` batch-marks every then-still-null registration for that event as viewed (`updateMany({ where: { eventId, viewedAt: null }, data: { viewedAt: new Date() } })`, run directly in the page's own Server Component body — a plain-mutation-during-a-GET-render is unusual but deliberate here, the same "mark as read on open" idiom used all over the web). `SiteHeader` computes this count once (only when logged in) and passes it down to `AccountMenu` as a prop, alongside `displayName`/`admin`.
  - **The badge itself is a real `<Link>`, not just a decorative count** — `getLatestOpenRequestHref(userId)` (same file) finds the single most recent open item (whichever of the newest `PENDING` `ContactRequest` or newest un-viewed `EventRegistration` has the later `createdAt`) and returns a URL with a `#`-anchor pointing straight at that one row: `/projekte/[id]/anfragen#anfrage-<id>` or `/projekte/[id]/termine/[eventId]/anmeldungen#anmeldung-<id>` (both list pages give each row a matching `id`+`scroll-mt-4`, same anchor-and-scroll convention as `/admin/nutzer`'s per-user rows). Returns `null` (no link, badge doesn't render) when the one open item is an `EventRegistration` on an organisation-only event with no `listingId` — `/anmeldungen` is always nested under a listing id, so there's no route to link to for that case. The badge deliberately lives **outside** the `<details>`/`<summary>` (a sibling in a shared `relative` wrapper, positioned to visually sit on the trigger's corner) rather than nested inside the `<summary>` — an interactive element nested inside another interactive element (the summary's own click-to-toggle) would make the badge's own click behavior unreliable.

## E-Mail-Verifizierung & CAPTCHA (`User.emailVerified`, Cloudflare Turnstile)

The contact form (`submitContactRequest`, see Kontaktanfragen above) had no bot-defense at all — anyone, logged in or not, could submit arbitrarily. The product decision: a registered **and email-confirmed** user skips CAPTCHA entirely; everyone else (anonymous visitors, and logged-in users who haven't confirmed their address yet) must pass Cloudflare Turnstile. "Registered" alone isn't treated as a trust signal, since a throwaway/unowned email address is exactly as easy to fake as filling in a plain contact form — only a clicked confirmation link proves the account owner actually controls that inbox.

- **Schema reuse, no migration needed**: `User.emailVerified` (`DateTime?`) and `model VerificationToken { identifier; token; expires; @@unique([identifier, token]) }` are both standard Auth.js/PrismaAdapter fields that already existed in `schema.prisma` (originally meant for Auth.js's Email/magic-link provider, never used since this app only has Credentials + Google) — repurposed here for a custom verification-link flow instead of adding new columns.
- **`src/lib/verification-token.ts`**: `createVerificationToken(email)` deletes any prior token(s) for that email and creates a new 64-char hex token (`crypto.randomBytes(32).toString("hex")`) with a 24h expiry. `sendVerificationEmail(email, token)` builds a `${SITE_URL}/verifizieren?token=...&email=...` link and sends it via the existing `sendMail()` (`src/lib/mailer.ts`, same optional-SMTP pattern as Kontaktanfragen's notification emails — silently no-ops with a console warning when SMTP isn't configured, so local dev never depends on real mail credentials). `verifyEmailToken(email, token)` looks the token up by its composite `identifier_token` key and **deletes it regardless of outcome** — single-use even on a failed attempt, so a guessed-wrong token can't be retried against the same row, while a *different* still-valid token for that email is untouched (verified directly: a wrong-token attempt returns `false` without disturbing the real token, which then still verifies correctly afterward) — then checks it isn't expired and sets `User.emailVerified` via `updateMany({ where: { email } })`.
- **`/registrieren`'s `registerUser`** (Credentials-based registration, `src/app/registrieren/actions.ts`) calls `createVerificationToken`/`sendVerificationEmail` right after `prisma.user.create`, before redirecting to `/anmelden?registriert=1` — a fresh Credentials account starts out unverified.
- **`/verifizieren`** (`src/app/verifizieren/page.tsx`) is a plain Server Component page that reads `{ token, email }` from `searchParams` and calls `verifyEmailToken` directly during render — the same "mutate as a side effect of a GET render" idiom already used for marking `EventRegistration`s as viewed (see Kontaktanfragen above), since a link clicked from an email client can only ever produce a GET request; there's no separate "confirm" step to add beyond the click itself. Shows a success message (with a link to `/anmelden`) or an error message pointing to `/mein-konto`'s resend button.
- **Google sign-in auto-verifies**: `src/lib/auth.ts`'s Auth.js config adds an `events.createUser({ user })` hook that immediately sets `emailVerified` — this event only fires for adapter-created users, i.e. a brand-new OAuth sign-in, never for Credentials registration (which creates its `User` row directly via `prisma.user.create` in `registerUser`, bypassing the `PrismaAdapter` entirely) — so a Google account is trusted as already address-confirmed (Google itself verified it), while a Credentials account still has to click the emailed link.
- **`/mein-konto`** (`src/app/mein-konto/page.tsx`/`actions.ts`) shows the current verification status next to the email field (a green "✓ Bestätigt", or an amber "Nicht bestätigt" message) and, only when unverified, a small separate `<form action={resendVerificationEmail}>` button that creates+sends a fresh token. Changing the email address in the "Persönliche Daten" form (`updateProfile`) resets `emailVerified` back to `null` and sends a new verification email to the *new* address — an email change is exactly as unverified as a brand-new signup until the new inbox is confirmed again.
- **Cloudflare Turnstile** (chosen over Google reCAPTCHA specifically for having no Google tracking): `src/lib/turnstile.ts` exports `turnstileEnabled = Boolean(process.env.NEXT_PUBLIC_TURNSTILE_SITE_KEY)` (optional at the infra level, same pattern as `ANTHROPIC_API_KEY`/`NEXT_PUBLIC_MAPTILER_KEY` — CAPTCHA is simply off everywhere while unset) and `verifyTurnstileToken(token, remoteIp)`, which POSTs to Cloudflare's `siteverify` endpoint and **fails closed**: a missing token, a missing `TURNSTILE_SECRET_KEY`, a non-OK response, or any thrown error all return `false` (blocks the submission) rather than defaulting to "allow" — a broken CAPTCHA config should block anonymous submissions, not silently disable the protection it exists for. `getClientIp` (already built for the Statistik feature, `src/lib/ip-lookup.ts`) supplies the `remoteip` parameter.
- **Zero client-side React state, matching this app's plain-form convention**: the widget is just `<script src="https://challenges.cloudflare.com/turnstile/v0/api.js" async defer />` + `<div className="cf-turnstile" data-sitekey={...} />` inside `ListingDetail`'s contact-form `<section>` (`src/components/listing-detail.tsx`) — Cloudflare's script auto-renders any matching div and injects its own hidden `cf-turnstile-response` input, submitted as part of the normal `<form action={submitContactRequest}>` like every other field. Only rendered when `requireCaptcha` (a prop computed per-request, see below) is true; when shown, it's accompanied by a hint pointing anonymous/unverified visitors at `/registrieren` ("Registrierte und bestätigte Nutzer:innen können Nachrichten ohne CAPTCHA senden").
- **Both `/projekte/[id]/page.tsx` and `/projekte/page.tsx`'s inline pane** compute `requireCaptcha = turnstileEnabled && !viewer?.emailVerified` (`viewer` is the logged-in user's `name`/`email`/`emailVerified`, fetched only when a session exists) and pass it down to `ListingDetail`, alongside a new `viewerContact={{ name, email }}` prop that pre-fills the `senderName`/`senderEmail` inputs via `defaultValue` for any logged-in visitor (previously the form was never pre-filled at all, regardless of login state).
- **`submitContactRequest` (`src/app/projekte/[id]/actions.ts`) re-checks server-side**, independent of whatever the client-side widget did or didn't render — the only check that actually matters: it looks up `session.user.id`'s `emailVerified` fresh (not trusted from any client-supplied value), and only when `turnstileEnabled && !isVerifiedSender` does it read the form's `cf-turnstile-response` field and call `verifyTurnstileToken`; a failed/missing token redirects back with `?error=captcha`, rendered by `ListingDetail` as an error banner above the form.
- **Env vars**: `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (public, embedded in the widget's `data-sitekey`) and `TURNSTILE_SECRET_KEY` (server-only, used against Cloudflare's `siteverify`) — both wired into `docker-compose.yml`'s `web.environment` block (passthrough from the root `.env`, same pattern as every other optional feature-gating key in this app). Both need to be added to `.env` once a Cloudflare Turnstile site is set up in the Cloudflare dashboard; until then, `turnstileEnabled` is `false` and the contact form has no CAPTCHA gate at all (same graceful-off behavior as every other optional integration here).

## Homepage-Feld & KI-Import (`Listing.homepageUrl`)

Every `Listing` has an optional `homepageUrl` column plus a `lastAiImportAt` timestamp (both nullable, added via migration). The field is edited via the shared `src/components/homepage-import-field.tsx` (`HomepageImportField`, client component), rendered inside `listing-form-fields.tsx`'s "Grunddaten" fieldset on both the create (`/projekte/neu`) and edit (`/projekte/[id]/bearbeiten`) forms — `ListingFormFields` takes an optional `listingId` prop (unset on the create page, the real id on the edit page) and an `aiImportEnabled` boolean, both threaded through to this component.

- **URL normalization** (`src/lib/normalize-url.ts`'s `normalizeHomepageUrl`) runs on every save through the normal form (`createListing`/`updateListing`), not just through the AI import path: a missing `http(s)://` scheme is prepended, and any *other* explicit scheme (`ftp://`, `file://`, `javascript:`, `mailto:`, `data:`, ...) is rejected outright (`null`) rather than having `https://` blindly prepended to it.
- **Three-phase flow: extract → review → apply.** An earlier version of this feature wrote every extracted field straight to the `Listing` and redirected immediately — no review step, and it would silently overwrite a field the owner had already filled in with whatever the AI found instead. Per explicit product decision, it now:
  1. **Start** (`startHomepageImport`, `src/app/projekte/homepage-import-actions.ts`, called directly from client code like `reorderListingMedia` — see Reorderable photo galleries above): creates the minimal draft `Listing` if there's no `listingId` yet (create page), sets `lastAiImportAt` immediately (the cooldown must gate the *attempt*, not just a successful one — this is the only real abuse guard on an otherwise free-standing, paid LLM call), then schedules the actual extraction via `after()` and returns a job id right away.
  2. **Poll** (`getHomepageImportStatus`, polled every 700ms by `HomepageImportField`): surfaces a live "was gerade passiert" status string from `src/lib/homepage-import-progress.ts` (a plain module-level `Map<jobId, ...>`, same rationale/shape as the demo-data generator's own progress store — see Demo data generators) — "Lade Homepage…", "Lade Filteroptionen…", "Analysiere Inhalt mit KI…", "Suche Standort…", "Fertig." — while `runHomepageExtraction` (`src/lib/homepage-import.ts`) does the actual work in the background.
  3. **Review**: once done, the client renders every field where the AI actually proposed something *different* from the Listing's current value as one row (current value struck through, proposed value below it) with its own checkbox, plus an "Alle auswählen" master checkbox above them all that checks/unchecks every row at once. **A field that's already filled in on the Listing defaults to unchecked**; an empty field defaults to checked — so the common case ("fill in what's missing") needs zero clicks, and protecting already-curated data from being overwritten means deselecting it, or just never checking "Alle auswählen" in the first place. Clicking "Übernehmen" calls `applyHomepageImport(listingId, jobId, result, selections)`, which persists only the checked fields and **redirects to `/projekte/<id>/bearbeiten?importiert=1`**, same as before.
- **Extracted fields**: `motto`, `howWeLive` (400–600 words HTML, tag-restricted same as `sanitizeRichText()`'s allowlist), `contactName`/`contactPhone`/`contactEmail`, the full address (`street`/`houseNumber`/`postalCode`/`city`/`state`/`country` — reviewed as one combined "Standort" row, not six separate ones, since they're one logical unit), `groupSizeCurrent`/`groupSizePlanned`/`freeSpots`, `costOneTime`/`costMonthly`, and three `AttributeGroup` selections (`geschlechterverteilung`/`projekt-typ`/`projekt-status`) plus `ListingCategory` ("Art des Inserates", multiple allowed) — plus `eventHints: string[]` as before (never creates `Event` rows, just a text suggestion in the redirect's flash banner).
- **Attribute/category matching via JSON-schema `enum`, not free text**: before calling the LLM, `runHomepageExtraction` fetches the actual `AttributeOption` names for those three groups and every `ListingCategory` name, and builds each of those schema properties with `enum: [...namesFromTheDatabase]` (`nullableEnum()`) — the model can only pick one of the real option names (or `null`), never invent its own, which is what actually makes it possible to reliably resolve a proposed value back to a real row id afterward (`findOptionId`/`findCategoryIds` in the same file) for `applyHomepageImportResult` to assign.
- **Claude's structured-output schemas cap out at 16 union/`anyOf`-typed parameters** ("Schemas contains too many parameters with union types... exponential compilation cost" — a real 400 error hit directly while building this, with 19 nullable fields). Fixed by only using a true `anyOf: [{enum}, {null}]` for the three attribute/category enums, which genuinely need a `null` branch distinct from any valid option name; every plain string/integer field instead uses a *sentinel* — an empty string, or `-1` for integers — meaning "nothing found" (`optionalString`/`optionalInt`, vs. the enum fields' `nullableEnum`), converted back to a real `null` right after parsing the model's response (`orNull`/`intOrNull`). This dropped the union count from 19 to 3.
- **Geocoding** (`src/lib/geocode-address.ts`'s `geocodeAddress()`) runs server-side against Nominatim whenever the extraction found a street/postal code/city — every other geocoding path in this app is client-side against `/api/geocode` (see Data model above), but the import pipeline has no browser round-trip to do that from, so this duplicates that route's Nominatim call directly. On success, `applyHomepageImportResult` sets both the plain `latitude`/`longitude` columns and the PostGIS `location` point via `setListingLocation()` (see Data model), exactly like the manual address-fields flow does.
- **`applyHomepageImportResult`** (`src/lib/homepage-import.ts`) persists only what's in `selections`: plain fields via one `prisma.listing.update`; the address (if checked) via that same update plus `setListingLocation`; each attribute-group selection (if checked) by deleting any existing assignment in that specific group and creating the new one (these are exclusive single-value groups per listing); the category selection(s) (if checked) via `upsert` per id (never removes an existing category the AI didn't re-propose); and — always, ungated by any checkbox, since it's purely additive and was never a "field with a current value to protect" — downloads and stores whatever candidate images `extractImageUrls` found, exactly like a manual upload (`processAndStoreImage`, appended after the current max `position`).
- **SSRF-safe fetching** (`src/lib/safe-fetch.ts`): fetching a user-supplied URL server-side is a real SSRF vector (internal network, cloud metadata endpoints), so `fetchPublicText`/`fetchPublicBuffer` only allow `http`/`https`, resolve the hostname via DNS and reject private/loopback/link-local/reserved IPv4 and IPv6 ranges, and — critically — **never follow redirects automatically** (`redirect: "manual"`): each hop (max 3) is manually re-resolved and re-validated against the same IP-range check before being followed, since a public-looking URL that redirects to an internal address would otherwise bypass the initial check entirely.
- **Text/image extraction** (`src/lib/homepage-scrape.ts`) is deliberately regex/tag-strip based (`extractReadableText`/`extractImageUrls`) rather than pulling in an HTML/DOM parser dependency — good enough for "best effort" extraction feeding an LLM, not a claim of correct HTML parsing. Images are capped at 8 candidates, filtered by filename (`logo`/`icon`/`favicon`/...) to skip obvious non-photo assets.
- **Env var**: `ANTHROPIC_API_KEY`, added to `docker-compose.yml`'s `web` service `environment:` block (passthrough from the root `.env`, same as `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`) — optional at the infra level, but the KI-Import button and its whole pipeline are unreachable without it.

## Performance: fehlende Indizes nachgetragen

A direct audit against the running database (`pg_indexes`) found several tables with no index beyond their primary key, despite being looked up by a non-PK column on essentially every `/projekte`/`/termine` page load:

- `ListingAttributeOption`/`EventAttributeOption` (`@@index([optionId])`) — every attribute-group filter (`some: { optionId: { in: [...] } }`) looked these up by `optionId`, but the existing composite PK (`[listingId, optionId]`/`[eventId, optionId]`) only helps a lookup leading with `listingId`/`eventId`, not `optionId` alone.
- `ListingCategoryAssignment` (`@@index([categoryId])`) — same reasoning, for the "Art des Projektinserates" category filter.
- `Media` (`@@index([listingId])`, `@@index([eventId])`) — every gallery fetch and map popup "business card".
- `ContactRequest` (`@@index([listingId])`) — `/projekte/[id]/anfragen`, the `/meine-projekte` pending-count badge, and the open-requests header badge.
- `EventRegistration` (`@@index([eventId])`) — `/anmeldungen` and the open-requests badge.

Separately, neither `Listing.location` nor `Event.location` (the PostGIS points used for Umkreissuche's `ST_DWithin` radius search) had a spatial index at all, despite `src/lib/geo.ts`'s own comment claiming one existed — every radius search was doing a sequential scan computing `ST_DWithin` per row rather than pruning candidates via an index first. Since `location` is `Unsupported("geometry(Point, 4326)")` in Prisma's type system, this couldn't be expressed as a schema.prisma `@@index` and instead lives in its own hand-written migration (`prisma/migrations/20260803130500_add_location_gist_indexes/migration.sql`, `CREATE INDEX ... USING GIST ("location")` on both tables) — the other seven indexes above came from a normal `@@index` in `schema.prisma` plus `pnpm db:migrate`.

## Security-Audit (`pnpm audit`)

`pnpm audit` (run from `apps/web`) surfaces known CVEs. As of this writing, 4 of the originally-found 7 advisories are pinned via `apps/web/pnpm-workspace.yaml`'s `overrides` block (`sharp: '>=0.35.0'`, `postcss: '>=8.5.18'`) — both were transitively bundled by Next.js's own dependency tree (`next>sharp`, `next>postcss`) at older, vulnerable versions, not something this project's `package.json` could bump directly; `pnpm why <pkg>` confirmed a single, unified patched version resolves everywhere afterward. Note: **pnpm v10+ no longer reads a `pnpm.overrides` key inside `package.json`** (silently ignored with a warning) — overrides belong in `pnpm-workspace.yaml` now.

The remaining 3 advisories (`find-my-way`, `brace-expansion`, `valibot`) are all pulled in exclusively via dev-only tooling (`prisma dev`'s bundled dev server, ESLint's glob matching) — never present in the production `next build`/`next start` runtime, so left unpatched pending upstream fixes from Prisma/ESLint's own dependency trees rather than forcing overrides for paths this app never executes outside local development.

`sharp`'s CVEs (libvips memory-safety issues) are specifically about Next's built-in `/_next/image` optimizer — checked directly: only `/ueber-uns`'s static portrait photo uses `next/image` anywhere in this app, every user-uploaded photo/gallery image deliberately renders via a plain `<img>` instead (see Media/storage sections above), so the real exposure to untrusted image input was low even before pinning the override.

## Commands

Run everything via Docker (starts Postgres/Valkey/Meilisearch/MinIO and the Next.js dev server together):
```bash
docker compose up
```
The app is then served at http://localhost:3000, with dependent services bound to 127.0.0.1 on their default ports (Postgres 5432, Valkey 6379, Meilisearch 7700, MinIO 9000/9001).

Run app/package commands inside the running container (see the host-vs-container note above):
```bash
docker compose exec web sh -c "cd /workspace/apps/web && <command>"
```
Common commands:
```bash
pnpm dev             # dev server on 0.0.0.0:3000 (already running via docker compose up)
pnpm build           # production build
pnpm lint            # eslint
pnpm exec tsc --noEmit   # type-check only

pnpm db:migrate      # prisma migrate dev — create/apply a migration from schema changes
pnpm db:seed         # prisma db seed — runs prisma/seed.ts (categories, attribute groups, and — outside NODE_ENV=production — a dev admin login)
pnpm db:studio       # prisma studio — browse the dev database
pnpm exec prisma generate   # regenerate the client into src/generated/prisma (also runs on postinstall)
```
Note: `apps/web/.env` holds a host-reachable `DATABASE_URL` (`localhost:5432`) for any tooling invoked from outside Docker; inside the `web` container, `docker-compose.yml`'s `environment:` block (hostname `postgres`) takes precedence over `.env` — both point at the same `c1u3`/`c1db3` database.
