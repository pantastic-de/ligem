# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Leben in Gemeinschaft" (ligem, homepage: ligem.de) is a free, common-good-oriented (gemeinwohlorientiert) international platform for all forms of communal living (WGs, Ökodörfer, Co-Housing, Mehrgenerationenhäuser, etc. — not limited to classic WGs). It serves four audiences at once: (1) housing communities presenting themselves / looking for new members, (2) common-good organizations working on communal-living topics, (3) people just informing themselves about communal living (regardless of search intent), (4) organizations/communities posting events, info sessions, or visiting days to a shared calendar. Deliberately **not** styled as spiritual/esoteric, even though a large part of the target audience personally is — tone and design stay neutral/grounded (see the `warm-community-design` skill under `.claude/skills/`).

Key product decisions (from the founder's requirements questionnaire, kept in memory for full detail):
- No automated matching — users only search/filter themselves.
- Listing taxonomy (room, whole unit, project founding, temporary stays, ...) is a freely extensible DB table, not hardcoded; a listing can belong to multiple categories.
- Required fields per listing are deliberately minimal (project name + owner); the long list of possible filters (location, lifestyle, values, decision model, ecology, ...) is explicitly a later expansion, not MVP scope.
- Guest access without login, moderation/approval before publishing, contact details revealed only after the listing owner approves.
- Multi-language content is planned (start: German + English).

Note: the founder's questionnaire originally listed Laravel as a tech preference, but the user has confirmed (2026-07-27) that the project stays on the existing Next.js/React/TypeScript stack below — no migration planned.

The Next.js app has a real domain data model (Prisma schema + migration applied) and a first vertical slice of UI: registration/login, submitting a listing, browsing published listings, and contacting a listing owner (see Pages below).

## Architecture

- Monorepo layout: the Next.js app lives in `apps/web`; the repo root only holds Docker/infra config. There is a root `pnpm-workspace.yaml`-style setup but currently a single app package.
- `docker-compose.yml` at the repo root defines the full dev stack:
  - `postgres` — PostGIS-enabled Postgres (user `c1u3`, db `c1db3` — the actual initialized credentials in the `postgres_data` volume; `DATABASE_URL` must match these, not a nicer-looking placeholder)
  - `valkey` — Redis-compatible cache/queue store
  - `meilisearch` — search engine (likely for searching WGs/orgs/listings)
  - `minio` — S3-compatible object storage (photos/videos/documents on listings)
  - `web` — runs the Next.js app itself via `pnpm dev` inside a `node:22-bookworm` container, with `DATABASE_URL`, `REDIS_URL`, `MEILISEARCH_HOST`/`MEILISEARCH_KEY`, `S3_ENDPOINT`/`S3_ACCESS_KEY`/`S3_SECRET_KEY`, `AUTH_SECRET`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` wired in as env vars
- Secrets/config for the compose stack come from a root `.env` (gitignored): `POSTGRES_PASSWORD`, `MEILI_MASTER_KEY`, `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD`, `AUTH_SECRET`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (Google OAuth is optional — the provider is only registered in `src/lib/auth.ts` when both are set).
- `apps/web` is a standard Next.js App Router project (TypeScript, React 19, Tailwind CSS v4, ESLint 9 flat config). Source lives under `apps/web/src/app`. Path alias `@/*` maps to `apps/web/src/*`.
- **Running commands inside the container vs. on the host is not interchangeable here.** `node_modules` was first installed by the `web` container (pnpm store path `/workspace/.pnpm-store/v11`); running `pnpm` from the host fails with `ERR_PNPM_UNEXPECTED_STORE` because the bind-mounted path resolves differently. Run `pnpm`/`prisma` commands via `docker compose exec web sh -c "cd /workspace/apps/web && <cmd>"` unless you've set up a separate host-side store.

## Data model (Prisma)

- Schema: `apps/web/prisma/schema.prisma`. Config (datasource URL, migrations path, seed command) lives in `apps/web/prisma.config.ts`, **not** in the schema file — this is Prisma 7, which moved connection handling to driver adapters (see below) and dropped `datasource.url` from `schema.prisma`.
- Client generation: `generator client { provider = "prisma-client" }` generates plain TypeScript (not the old `prisma-client-js`) into `apps/web/src/generated/prisma/` (gitignored, regenerated via `prisma generate`, wired into `postinstall`). Import from `@/generated/prisma/client` (or `../src/generated/prisma/client` from `prisma/seed.ts`) — there is no barrel `index`.
- Prisma 7 requires an explicit driver adapter at runtime: `apps/web/src/lib/prisma.ts` builds a `PrismaClient` with `@prisma/adapter-pg` (`pg` driver), not a bare `new PrismaClient()`. Reuse that shared instance instead of instantiating a new client per file.
- PostGIS: enabled via `previewFeatures = ["postgresqlExtensions"]` and `extensions = [postgis]` on the datasource. Location columns (`Listing.location`, `Event.location`) are typed `Unsupported("geometry(Point, 4326)")` — Prisma Client can't read/write them directly, use `$queryRaw`/`$executeRaw` for anything geo (distance search, map clustering). Both `Listing` and `Event` keep plain `latitude`/`longitude` Float columns in sync with `location`: `src/lib/geo.ts` (`setListingLocation`/`setEventLocation`) pushes lat/lng into `location` via `$executeRaw` `ST_SetSRID(ST_MakePoint(lng, lat), 4326)` after every create/update; radius search (`/termine`) runs `$queryRaw` with `ST_DWithin(location::geography, ..., radiusMeters)` to get matching IDs, then a normal `findMany({ where: { id: { in } } })` for the rest.
- Geocoding: `src/app/api/geocode/route.ts` proxies OpenStreetMap's Nominatim (free, no API key, but rate-limited and requires an identifying `User-Agent` — already set) for both free-text place search (`?q=`) and structured lookups (`?postalcode=&city=&street=&country=`). All actual geocoding happens **client-side** — `src/components/address-fields.tsx` (Land/Bundesland auto-filled from PLZ, full-address geocode with a fallback to city-only if the street doesn't resolve or the result's postcode disagrees with the input, plus a Leaflet map to override by click or browser geolocation) and `src/components/location-radius-picker.tsx` (place search + radius slider, used by both `/termine` and `/projekte`'s search) both just populate hidden `latitude`/`longitude` form inputs — the server actions never geocode anything themselves, they only persist whatever coordinates arrived.
- `location-radius-picker.tsx` also draws an `L.circle` overlay sized to the selected radius (radius step in km × 1000) around the current point, and calls `map.fitBounds(circle.getBounds(), ...)` whenever the marker moves or the radius slider changes, so the visible map always matches the active search radius; picking "Alle" (the last slider step, radius `null`) removes the circle without forcing a specific zoom. The search-origin marker is a custom pin (`L.divIcon` with an inline SVG teardrop, no external image asset) rather than the plain `circleMarker` dot used for results, so "where I'm searching from" is visually distinct from "what was found". The map is created with `scrollWheelZoom: false` (scrolling the page over an embedded map shouldn't hijack the scroll into a zoom), is deliberately compact (`h-56`/`h-40`), and has a small "✕" button (top-right, overlaid) that hides it and swaps in a "👁️ Karte einblenden" button — hiding toggles a Tailwind `hidden` class on the *same* container div rather than conditionally rendering it, since removing/re-adding the div from the DOM would detach it from the already-created Leaflet map instance (the map is only ever constructed once, in a mount effect with an empty dependency array); un-hiding calls `map.invalidateSize()` on the next frame, since Leaflet doesn't notice its container resizing while `display: none`. The radius `<input type="range">` uses a `.ligem-radius-slider` class (defined in `globals.css`, since Tailwind has no utilities for slider thumbs) for a much larger (32px) thumb than the browser default — needed for reliable touch dragging on small screens. Within the `Umkreissuche` fieldset, the map comes first, with the "Ort eingeben"/"Suchen" row and the radius slider both rendered *below* it (not above, as originally built) — a deliberate reorder so the map is the first thing seen under the fieldset legend. "Meinen Standort verwenden" (geolocation, the same `useMyLocation()` as before) is a small `LocateFixed` (lucide-react) icon-button absolutely positioned *inside* the "Ort eingeben" input's right padding, rather than a separate labeled "📍 Mein Standort" button next to it — a more compact, established pattern (same idea as a search box's embedded clear/search icon).
- The small inline map (`h-56`/`h-40`) is too cramped to actually interact with once there are several result markers on it, so `location-radius-picker.tsx` also supports expanding it: a "⤢" button (bottom-right of the map — Leaflet's own zoom control already occupies top-left, and "✕ Karte ausblenden" occupies top-right, so this is the one free corner) sets `expanded`, which switches the map's **wrapper** div from normal in-flow layout to `fixed inset-0` — full-viewport fullscreen on mobile, `sm:inset-8 sm:max-h-[70vh] sm:max-w-4xl sm:rounded-2xl` (a centered, bordered box with breathing room to the screen edge) from `sm:` up — with a click-to-close semi-transparent backdrop (`fixed inset-0 bg-black/40`, a separate element behind it) rather than a fixed pixel height. A "✕ Karte verkleinern" button and Escape both close it too. This deliberately expands via an explicit button rather than "click anywhere on the map", since the map surface itself already needs clicks for panning/zooming/opening marker popups — an any-click-expands trigger would conflict with that. The expand button is styled to match Leaflet's own control buttons (`.leaflet-bar a`'s look: white 26×26px square, dark text, `box-shadow: 0 1px 5px rgba(0,0,0,.65)`) rather than the app's usual rounded surface buttons, so it visually reads as part of the map rather than as an unrelated app UI element floating on top of it.
- While expanded, the place-search input (`placeholder="Ort oder Region eingeben"`, plus the embedded `LocateFixed` icon) and the radius slider are rendered a second time as an `absolute inset-x-0 bottom-0` panel with a solid (not translucent) `bg-surface` background **overlaid on the bottom of the enlarged map itself**, not only below it — so they stay usable without shrinking the map back down first. Both call sites render the exact same `searchControls` JSX (a local variable holding that block, built once per render from the same controlled `placeQuery`/`radiusIndex` state) — normally below the map, or inside this overlay instead while `expanded`, never both at once — so toggling `expanded` can't leave two live copies of the same form controls in the DOM. Leaflet's own attribution control (default position bottom-right) would otherwise sit hidden behind this panel, so the `[mapVisible, expanded]` resize effect also calls `map.attributionControl.setPosition(...)`, moving it to `topleft` (stacking below the zoom control) while expanded and back to `bottomright` once collapsed.
  - **The div Leaflet actually calls `L.map()` on must keep a constant `className` string across every render.** `L.map(container)` adds its own classes (`leaflet-container`, `leaflet-touch`, ...) directly onto that element outside of React's knowledge; React's reconciler only re-applies the whole `class` attribute when the `className` *prop value* it computes differs from what it wrote on the previous render (it diffs against its own last-written value, not the DOM's actual current class list) — so as long as the JSX-computed string is identical to last time, React leaves the attribute alone and Leaflet's own classes survive untouched. The very first version of the expand feature broke this: it toggled that div's own className based on `expanded` (`"h-full w-full overflow-hidden"` vs. a fixed-height variant), so the moment someone expanded the map, React overwrote `class` with a string that didn't include `leaflet-container` — silently stripping Leaflet's base styling (the tile layer still rendered internally, positioned via inline `transform`s, but with no visible map surface at all). Fixed by moving every size/shape class (`h-56`/`h-40`/`rounded-xl`/the `fixed`-vs-`relative` toggle/etc.) onto the **wrapper** div one level up, which Leaflet never touches, and giving the actual `ref={mapRef}` div a hardcoded, always-identical `"h-full w-full"` className. The general rule this establishes: never let application state drive `className` (or anything else React fully owns) on a DOM node a third-party library also mutates directly — put reactive styling on a wrapper instead.
  - The same Leaflet container/instance is reused for both sizes (only the wrapper's CSS changes, no remount), so `invalidateSize()` plus a re-fit of the current view (selected-item focus or overview, see below) runs after every `mapVisible`/`expanded` transition, since Leaflet doesn't notice its container resizing on its own.
- Clicking the map does **not** set the search origin at all — there's no click handler for it. An earlier iteration required an explicit "📍 Standort auf Karte setzen" step (arming a `placementMode` so only the *next* click placed the marker) specifically to stop panning/zooming the results map from accidentally moving the origin, but once the origin could already be set via the place-name search or the `LocateFixed` geolocation icon (see above), that whole button/mode was dropped as redundant — a plain click on the map now just pans/zooms or interacts with markers/popups like any other Leaflet map, never the search origin.
- `fitOverviewView(L, map)` is the single place that decides what the map's view should show when no specific item is selected: the bounds of every result marker plus the search origin, **extended to always also include the full radius circle** when one is active. This replaced two independent `fitBounds` calls (one in the radius-circle effect, one in the results-layer effect) that used to race each other — moving the radius slider re-fetches a new (filtered) `resultItems` array a moment later, and whichever `fitBounds` happened to run last won, which could leave the circle only partially visible again right after it had just been fitted to it. Both effects now call this one function, so the circle is always included in the view regardless of which one fires last.
- `src/lib/category-color.ts` (`colorForCategory(id)`) deterministically hashes an `AttributeOption` id to one of eight warm-but-distinguishable colors (kept visually separate from the semantic success/warning/error tones so a category dot never reads as a status) — used to color-code "Veranstaltungsart" (event type) on the `/termine` calendar without needing a dedicated color column in the database. `/termine/page.tsx` builds a `Record<"YYYY-MM-DD", string[]>` from the already-fetched (filtered) `events` list and passes it through `termine-search-form.tsx` into `event-date-filter.tsx`, which renders up to 3 small colored dots under any day-cell that has matching events, plus a color legend (name + swatch, computed independently client-side from the same `veranstaltungsart` options via the same deterministic function, so it always matches without needing to be threaded through as extra data) below the calendar so the colors carry meaning rather than being purely decorative.
- `location-radius-picker.tsx` takes a `resultItems` prop (`MapResultItem[]` from `src/lib/map-result-item.ts` — `{id, label, sublabel?, type?, popupHtml?, latitude, longitude, href}`, plus the `escapeHtml` helper used when building marker popup/tooltip HTML); the found items are rendered as clustered markers **in the same map instance** as the origin pin/radius circle. Both `/projekte` and `/termine` use this merged single-map layout — there is no separate results map anymore. `renderResultsLayer(L, map)` (re)builds this marker-cluster layer and is called both from the mount effect (for the initial paint, since the map itself is only ready once the async `getLeafletWithCluster()` resolves) and from a `useEffect(() => {...}, [resultItems, selectedId])` — `resultItems` is a **new array on every filter-driven navigation** (each change to any filter re-renders the server-component page with a differently-filtered result set), so this dependent effect correctly rebuilds the layer every time a filter changes; an earlier version assumed the opposite (that `resultItems` "never usefully changes after mount") and only rendered once at mount, which silently left the map showing the very first load's markers forever regardless of later filtering — e.g. filtering down to 2 results still showed all the original markers. `location-radius-picker.tsx` always renders (even with zero geocoded items — it just falls back to a Germany-wide view) rather than being conditionally hidden, so newly published listings/events without coordinates yet don't suppress the map for everyone else's markers.
  - Each result marker's **permanent tooltip label is itself clickable**: `bindTooltip(..., { interactive: true })` (tooltips are non-interactive/`pointer-events: none` by default, which would otherwise let clicks fall through to the map underneath) plus `marker.getTooltip()?.on("click", () => marker.openPopup())` opens the marker's own popup. The popup itself uses `item.popupHtml` when the caller supplied one, otherwise falls back to a plain label+type link. `/projekte/page.tsx`'s `buildListingPopupHtml()` builds a small "business card" for listings: photo, project name (linked to the same inline `?projekt=<id>` detail pane via `item.href`), location, motto, Projekttyp/Kategorie badges, monthly cost, and a mini "Nächste Termine" list (up to 3, fetched in one batched `event.findMany({ listingId: { in: [...] } })` query rather than per-listing, each linked to its own `/termine/[eventId]` standalone page).
  - The marker cluster group also sets `spiderfyDistanceMultiplier: 3` and listens for its `spiderfied`/`unspiderfied` events to `closeTooltip()`/`openTooltip()` on the affected markers. Several markers can legitimately sit at (near-)identical coordinates (e.g. multiple events at the same listing's address), and clicking their cluster bubble while already at max zoom "spiderfies" them — fans them out a small fixed distance with connector legs — which isn't enough room for their *permanent* labels not to overlap into an unreadable mess; hiding labels for that brief fanned-out state (the markers are already visually separated and individually clickable/poppable without them) is simpler and more robust than trying to out-space the overlap.
- All map components use dynamic `import("leaflet")` inside `useEffect` (Leaflet touches `window` at module load, so it can't be a top-level import in code that might render on the server), plain `L.circleMarker` instead of the default pin icon for non-origin markers (sidesteps Leaflet's well-known marker-asset-path bug under bundlers), and a global `.ligem-event-label` CSS class in `globals.css` (Leaflet renders outside React's tree, so Tailwind utility classes don't reach it).
- **`leaflet.markercluster` bundler quirk**: its CJS build mutates the Leaflet *global* `L` directly (`L.MarkerClusterGroup = ...`) instead of `require("leaflet")`-ing its own reference, and the object returned by a dynamic `import("leaflet")` is a frozen ES module namespace object that can't have new properties added to it. `src/lib/leaflet-cluster.ts` (`getLeafletWithCluster()`) works around this with a **module-level singleton**: the first caller spreads the imported module into a plain mutable object, assigns it to `window.L`, awaits `import("leaflet.markercluster")` once, then caches that same object for every later caller. This isn't just cosmetic — `leaflet.markercluster`'s factory function only runs once per browser session (ES modules are cached), so if each map component created and discarded its own mutable copy instead of sharing one, only the very first mounted map would ever get a working `markerClusterGroup`; every later mount/remount (including plain re-renders and client-side navigations between `/projekte` and `/termine` within the same session) would silently get a copy missing the augmentation. `location-radius-picker.tsx` gets its `L` through this helper — use it for any new component that needs clustering rather than reimplementing the mutable-copy dance locally.
- **Global type and spacing scale** (`globals.css`, both later user-requested reductions from the original `warm-community-design` defaults — see that skill's Typografie/Barrierefreiheit sections for the accessibility trade-off this creates): `body`'s base font-size is `14.4px` (was 18px), and the `@theme inline` block redefines Tailwind's entire `--text-xs` through `--text-5xl` scale at the same ~20% reduction so utility classes and inherited body text stay proportional. Separately, `--spacing` (Tailwind v4's single base unit — every numeric utility, `p-*`/`m-*`/`gap-*`/`h-*`/`w-*`/`min-h-*`/etc., is `calc(var(--spacing) * N)`) is reduced from the 0.25rem default to `0.19rem` (~24%), which is what actually shrinks checkboxes/radios (`h-5 w-5`), the calendar grid (`event-date-filter.tsx`'s `gap-1` + `min-h-11` day cells), and every form control's `min-h-11`/`min-h-12` height — one variable instead of chasing each individually. Checkbox/radio *label text* additionally gets an explicit `text-sm` (the `"flex min-h-11 items-center gap-2"` wrapper pattern, used ~17x across `listing-form-fields.tsx`/`event-form-fields.tsx`/`*-search-form.tsx`/`registrieren`/`admin/attribute`/`admin/nutzer`), since it previously had no size class and so didn't shrink along with the rest via the body font-size alone. The `--spacing` change deliberately does *not* touch `--radius-*` (a separate Tailwind v4 scale) or the hand-tuned pixel values in `.ligem-radius-slider`/`.ligem-event-label` (both already deliberately sized, not part of the numeric utility scale).
- Media/photos go through MinIO, not through Prisma directly: `src/lib/storage.ts` wraps the `minio` client (bucket `ligem-media`, auto-created on first use) with `putObject`/`getObjectBuffer`/`deleteObject`. Since MinIO is only reachable inside the Docker network (bound to `127.0.0.1` on the host), `src/app/api/media/[...path]/route.ts` proxies/streams objects to the browser — image `<img src>`s point at `/api/media/<storageKey>`, never at MinIO directly. `Media` belongs to either a `Listing` or an `Event` (`listingId`/`eventId` both nullable, exactly one set — enforced in application code, not the DB). `src/lib/media.ts` (`processAndStoreImage`, `splitBySize`) holds the shared upload pipeline: resize with `sharp` at upload time into two stored JPEGs per photo — a display version (max width 1600) and a thumbnail (max width 400) — rather than resizing on every render; `src/app/projekte/[id]/media-actions.ts` (listings) and `src/app/projekte/[id]/termine/event-media-actions.ts` (events) both call it, each with their own ownership check. `Media.position === 0`'s thumbnail is the list-view image on `/projekte` and `/termine`. Files over 8MB are rejected per-file (`MAX_IMAGE_SIZE` in `src/lib/media.ts`); `next.config.ts`'s `experimental.serverActions.bodySizeLimit` is raised to `50mb` so the *framework's* 1MB-default request-body cap doesn't reject a multi-file batch before that per-file check even runs.
- Domain shape (full rationale in project memory — `ligem_positioning`, `ligem_roles_and_content_model`, `ligem_trust_legal_business`, `ligem_tech_and_design`):
  - **Auth**: `User`/`Account`/`Session`/`VerificationToken` follow the Auth.js Prisma-adapter shape. `UserRoleAssignment` lets one user hold several of `SUCHENDE`/`ANBIETER`/`MODERATOR`/`ADMIN` at once (no fixed role).
  - **Organizations** own multiple `Listing`s/`Event`s (Vereine/Genossenschaften as first-class actors, not just users).
  - **Listing** taxonomy (the "Art des Projektinserates" — Zimmer, ganze Einheit, ...) is DB-backed and many-to-many (`ListingCategory` + `ListingCategoryAssignment`), not a hardcoded enum. Only `projectName` + `createdBy` are required; everything else (Standort, Ansprechperson, Gruppengröße, Kosten, Suchzeitraum, ...) is optional real columns on `Listing`.
  - **Generic filter-attribute system**: `AttributeGroup` + `AttributeOption` is a general extensible-taxonomy mechanism sitting alongside `ListingCategory`, shared between Listings and Events via `AttributeGroup.appliesTo` (`LISTING`/`EVENT`) plus two separate join tables, `ListingAttributeOption` and `EventAttributeOption`. Listing-side groups: Projekt Typ, Projekt Status, Geschlechterverteilung, Organisationsform, Gemeinschaftsbereiche, Grundwerte, Wohnlage, Zielgruppe. Event-side groups: Veranstaltungsart, Zielgruppe, Merkmale. `AttributeGroup.allowMultiple` is a UI hint only (radio vs. checkboxes in the form) — the underlying relation is many-to-many either way, so new filter values (or whole new filter groups, for either target type) are just rows, managed from `/admin/attribute`, never a migration. There is no free-form `Listing.attributes` JSON column — it was removed once this system replaced it.
  - No matching engine anywhere in the schema — `SavedSearch.filters` is just a stored filter set for the user's own search UI (not built yet).
  - `ContactRequest` (contact form, not chat) only reveals the listing owner's contact info once `status` flips to `ACCEPTED`. `Appointment` is separate (Besichtigungstermin scheduling, not built yet). `Event` is the public calendar (Veranstaltungen/Besuchstage): listing owners manage their own under `/projekte/[id]/termine`, and everyone can browse/filter/search-by-radius the public calendar at `/termine`. Events carry `latitude`/`longitude` (plain columns, kept in sync with the `location` PostGIS point — see below), `websiteUrl`, `cost`, `maxParticipants`, `registrationRequired`; `EventRegistration` is the "send a message or sign up N participants" form on an event's public page — no accept/decline workflow, the organizer just sees a list (`/projekte/[id]/termine/[eventId]/anmeldungen`).
  - `Report` covers abuse reports across listings/events/orgs/users; there's deliberately no ban-history/audit subsystem, matching the "lightweight trust & safety" decision.
- Prisma also installed its own AI-agent skills under `apps/web/.claude/skills/prisma-*` (from `prisma init`) — check those for Prisma-7-specific syntax (driver adapters, config file shape) before assuming Prisma 5/6 patterns from training data.

## Authentication & authorization

`src/lib/auth.ts` configures Auth.js (`next-auth@5`) with `PrismaAdapter`, JWT sessions (required because of the Credentials provider), a `Credentials` provider (email + bcrypt-hashed password against `User.passwordHash`), and an optional `Google` provider gated on `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` being set. Route handler: `src/app/api/auth/[...nextauth]/route.ts`.
- `callbacks.jwt`/`callbacks.session` copy the user id onto `session.user.id` (not there by default with JWT sessions) — the type augmentation for this lives in `src/types/next-auth.d.ts`. Any code reading `session.user.id` depends on both files staying in sync.
- `src/components/site-header.tsx` is a server component that calls `auth()` directly, shows the "Admin" nav link only when `isAdmin()` is true, and renders a sign-out `<form>` whose action calls the exported `signOut`.
- `src/lib/authz.ts` has the admin-role check (`isAdmin(userId)`, checking `UserRoleAssignment` for `ADMIN`) plus `requireAdminPage()`/`requireAdminAction()` — every `/admin/*` page and every admin server action calls one of these; the page-level check alone is not enough since actions can be invoked directly.
- Ownership checks for listings/events are simpler: compare `session.user.id` to `Listing.createdById` directly (see `/projekte/[id]/bearbeiten` and `/projekte/[id]/termine/*`) — there's no multi-manager-per-listing concept yet, just a single owner.

## Pages

All *mutating* forms follow the same convention: a server-component page with a plain `<form action={serverAction}>` (no client JS/`useActionState`), where the action is a `"use server"` function in a sibling `actions.ts` that validates, mutates via Prisma, and calls `redirect()` — errors redirect back to the same page with an `?error=...` query param the page reads server-side. This works without JavaScript and keeps forms accessible; follow the same pattern for new forms rather than introducing client-side form state. The large "Projekt eintragen"/"Projekt bearbeiten" field set is factored into the shared `src/components/listing-form-fields.tsx` so create and edit stay in sync — extend that component, not one page's copy of it, when adding a field.

The `/projekte` and `/termine` **search/filter** forms are a deliberate exception — they don't mutate anything, so they auto-apply on every change instead of requiring a submit click. `src/lib/use-auto-submit-form.ts` (`useAutoSubmitForm()`) is the shared piece: it holds a `formRef`, and its `submitNow()` reads the form via `new FormData(formRef.current)`, builds a query string, and calls `router.replace(pathname + "?" + qs, { scroll: false })` (wrapped in `startTransition` for `isPending`), so the server component page re-fetches and re-renders without a full page reload; `handleChange()` is the same thing debounced 300ms, wired to the form's own `onChange` (native `<select>`/checkbox/radio changes bubble up to it for free). `src/components/projekte-search-form.tsx` and `src/components/termine-search-form.tsx` are client components that own the entire filter `<form>` (moved out of the respective page files, which stay server components and just pass in serializable data + current param values as `defaults`) — they have no submit button, and set `onSubmit={(e) => e.preventDefault()}` as a safety net (the "Ort eingeben" text field inside `LocationRadiusPicker` could otherwise implicit-submit on Enter). `LocationRadiusPicker` and `EventDateFilter` both take an optional `onChange?: () => void` prop, invoked (skipping the initial mount, via a ref guard) whenever their internal state changes through map clicks, place search, geolocation, the radius slider, calendar day clicks, or the date-range preset buttons — none of which are native DOM "change" events on the hidden inputs they update, so they can't rely on the form's own bubbling `onChange` and must call this callback explicitly instead.

Both pages also share the same responsive two-column layout: a page-level wrapper (`max-w-[1800px]`, no narrower cap — unlike every other page's `max-w-2xl`-ish wrapper, these two are meant to use the full browser width on desktop) contains a `flex flex-col lg:flex-row` split — a fixed sidebar column for the search form (map included) and a `flex-1 min-w-0` column for results. Below `lg`, it's a single stacked column (form above results) matching every other page's mobile-first layout; nothing here is sticky. The result `<ul>` itself switches from `grid-cols-1` to `xl:grid-cols-2` — a second breakpoint step, one narrower than the page-level split — since right after the page splits into two columns the results column alone often isn't wide enough yet for two result cards side by side without feeling cramped.

Both `/projekte/page.tsx` and `/termine/page.tsx` keep their sidebar at `lg:w-[380px]`, deliberately narrow so the results column gets as much of the page's width as possible — `termine-search-form.tsx` stacks `EventDateFilter` above `LocationRadiusPicker` as plain siblings (not a side-by-side grid) specifically to keep that sidebar narrow rather than needing extra width to fit a calendar and a map next to each other. ## Demo data generators

The core generator logic lives under `apps/web/src/lib/demo-data/` (`shared.ts`, `listings.ts`, `events.ts`, `long-description.ts`, `cleanup.ts`) and creates synthetic, clearly-fake `Listing`/`Event` rows (with real photos from Lorem Picsum, real geo-spread across both 32 real big German/Austrian/Swiss cities and 20 real small villages/towns, and randomized attributes/categories) to exercise the `/projekte` and `/termine` search and filter UI at realistic volume. It exists because scraping real communities' data from other platforms for this purpose would raise ToS, copyright, and GDPR/consent problems — synthetic data sidesteps all of that.
- **Every generated project name/motto/"So leben wir"/"Wen wir suchen" and every event title/description is unique**, not picked from one small fixed pool. `listings.ts`/`events.ts` compose each value from several independent word/sentence banks (e.g. `NAME_STEMS` × `NAME_SUFFIXES` for names, `ABSURD_TOPICS` × a per-theme title template for events) — each bank entry is a grammatically self-contained fragment (a whole sentence, or a whole compound-noun part), so any recombination stays coherent; there's no mid-sentence word-swapping that could produce broken German. `pickUniqueComposed(build, used)` in `shared.ts` retries the `build()` closure until it produces a string not already in `used` (a few hundred attempts against a combinatorial space in the thousands essentially never exhausts it) and adds it; `used` is seeded from values already in the database (not just the current batch), so generating another batch later still can't collide with what's already there.
- `shared.ts`'s `pickLocation()` picks a listing's location from either `CITIES` (32 big cities) or `VILLAGES` (30 small real villages/towns, added so demo listings aren't all clustered in major cities), weighted 88% village/12% city — raised twice from an original 45/55 split (then 60%, then this) since each prior weighting still read as too city-heavy in practice; note this only reshapes newly generated listings; the already-accumulated dataset keeps whatever mix it was generated with until cleared and regenerated via `/admin/demo-daten`.
- **`howWeLive`/`whoWeAreLooking`/event `description` are generated as HTML**, not plain text — matching what a real submission through `RichTextField` (see below) would produce, and using only tags its sanitizer allows (`p`, `strong`, `em`, `ul`, `ol`, `li`, `br`): `long-description.ts`'s `buildLongDescriptionCandidate()` wraps each of its four sections (intro, building, people, closing) in its own `<p>`; `listings.ts`'s `buildWhoWeSeekCandidate()` renders as a two-item `<ul>` when both sentence slots roll a value, otherwise a single `<p>`; `events.ts`'s `buildDescriptionCandidate()` wraps `kurz`/`ganztag` descriptions in one `<p>`, and gives `mehrtaegig` (multi-day) events a real `<ol>` day-by-day program instead of the previous newline-joined plain text.
- **"So leben wir" is a long (~200-400 word), deliberately absurd/over-the-top narrative**, generated by `long-description.ts`'s `buildLongDescriptionCandidate(cityName, isVillage)` rather than the old three-short-sentence system. It picks one random `Theme` (each with its own `opener`/`building`/`people`/`closer` sentence banks) and composes: 1 opener, 2 region-flavor sentences (a separate `VILLAGE_REGION_FLAVOR`/`CITY_REGION_FLAVOR` bank depending on `isVillage`, so the prose frames the location as rural or urban correctly), 4 building and 4 people sentences (via `pickNDistinct`, so a single generated text never repeats a sentence), and 2 closers — enough sentences to reliably land in the 200-400 word target given each bank's sentence length. The content deliberately centers on **communal-living substance rather than individual hobby/personality gimmicks** (an earlier version leaned on things like a music-genre-obsessed theme, which read as too gimmicky and got replaced): `kooperation` (mutual aid), `wertschaetzung` (appreciation & care), `achtsamkeit` (mindfulness), `konflikte` (conflict handling), `entscheidungsfindung` (consensus/discourse), `rechte-privilegien` (fairness/equity), `alltag-aktivitaeten` (shared daily-life planning), `ernaehrung` (food/dietary preferences), `politik-gesellschaft` (political/societal discourse) — plus a handful of lighter personality-flavor themes (`handwerk`, `yoga`, `spirituell`, `okkult`, `sekte`, `spiessig`, `nerd`) kept for variety. Each theme's `people` bank includes a short illustrative "Zuletzt gab es eine Diskussion darüber, ob …" vignette, so the text shows concrete examples of the group actually discussing these topics rather than just asserting the theme abstractly.
- **Event titles/descriptions intentionally span a much wider range of absurdity** than the original "esoteric commune" flavor alone: `ABSURD_TOPICS` (events.ts) now also covers Garten, Waldbaden, harmless kleinteilige Schwurbel-Satire (mundane things like the laundry schedule or a missing garden fork dressed up in conspiracy-theory language — deliberately not referencing real harmful conspiracy ideologies), legal-and-tasteful alternative-scene topics (Tantra, Kuschelparty, Polyamorie, FKK), and absurd hobby/animal combinations (dinosaur riding, keeping an orca in the bathtub, alpaca yoga) — all still just entries in the same shared pool used by `infotag`/`workshop`/`vortrag`/`online` titles, plus smaller additions to `MITMACHTAG_ACTIONS`/`BESUCHSTAG_TOPICS`/`FEST_OCCASIONS`.
- **Primary way to run it: `/admin/demo-daten`** (ADMIN-only, linked from `/admin`). The "Demo-Projekte generieren"/"Demo-Termine generieren" forms show a live progress bar while a batch runs, since generating even a modest count can take minutes (each row fetches a photo and writes several related rows) — far too long to hold a single request/response open. This is the one pair of mutating forms in the app that isn't a plain `<form action={...}>` (see the convention described under Pages): `src/components/demo-data-generate-form.tsx` (`DemoDataGenerateForm`, client component) calls a `start(count)` server action directly (`startGenerateListings`/`startGenerateEvents` in `src/app/admin/demo-daten/actions.ts`), which clamps the count, creates a job via `src/lib/demo-data/progress-store.ts`, and schedules the actual `generateDemoListings`/`generateDemoEvents` call inside `after()` (from `next/server`) — Next's sanctioned way to keep work running after the response has already been sent, rather than a bare unawaited async IIFE. `startGenerate*` returns the job id immediately; the client then polls a second action, `getGenerateProgress(jobId)`, every 700ms and renders a progress bar + "`completed / total`" text (plus the most recent item's label) until the job reports `done`, then calls `router.refresh()` to pull the updated demo-data counts. `progress-store.ts` is a plain module-level `Map<string, ProgressState>` — deliberately not Redis/Valkey-backed, since the app runs as a single long-lived Node process (`pnpm start`, not serverless) and this is a low-stakes admin dev tool; jobs are pruned a few minutes after completion. `generateDemoListings`/`generateDemoEvents`'s `onProgress` callback signature is `(current, total, message)` (numeric, not a pre-formatted string), used both by the admin UI's job store and by the CLI scripts' plain `console.log`. A third, destructive form calls `deleteAllDemoData()` behind a `ConfirmSubmitButton` (`src/components/confirm-submit-button.tsx`, a thin client-side `confirm()` wrapper used for the few genuinely irreversible admin actions) — this one stays a normal blocking form action, since deletion is fast enough not to need progress feedback.
- Each listing gets **3-6 photos** (`randomInt(3, 6)` in `listings.ts`, up from 1-2), enough to exercise the real multi-photo gallery (see `PhotoGallery` under Pages) rather than always hitting its single-photo fallback.
- **`searchPeriodStart`/`searchPeriodEnd`** are generated as a realistic pair rather than two independently-random dates: a start date (`chance(0.7)` of having one at all) plus either a week-length window, a month-length window, or no end date at all (an open-ended "looking from this date onward") — see the `periodLength` pick in `listings.ts`. This feeds `/projekte`'s "Suchzeitraum" advanced-search filter (see Pages).
- Every `Listing` created by the generator gets `isDemo: true` — this (not the historical email-domain check) is the source of truth for "is this demo data" everywhere in the app now, including the moderation queue below.
- Demo `User` accounts additionally get an email on the IANA-reserved `.invalid` TLD (`@ligem-demo.invalid`). **`Listing.createdById`/`Event.createdById` are `ON DELETE RESTRICT` in the actual database, not cascade** — a plain `DELETE FROM "User"` fails the moment any demo Listing/Event still references it. `deleteAllDemoData()` therefore deletes demo Events, then demo Listings, then the Users themselves, in that order (Media/attribute-option/category rows hanging off Listings/Events *do* cascade per schema.prisma, so those disappear automatically; the actual MinIO objects behind Media rows don't, and are deleted manually before the rows are removed).
- `apps/web/scripts/generate-demo-listings.ts` and `generate-demo-events.ts` still exist as thin CLI wrappers around the same `src/lib/demo-data/*` functions, for bulk/scripted use outside the browser:
  ```bash
  docker compose exec web sh -c "cd /workspace/apps/web && pnpm exec tsx scripts/generate-demo-listings.ts --count=50"
  docker compose exec web sh -c "cd /workspace/apps/web && pnpm exec tsx scripts/generate-demo-events.ts --count=100"
  ```
  `generate-demo-events.ts` only attaches events to existing demo listings (`isDemo: true`), so run the listings script (or the admin form) first. Listing counts are clamped to 1-100, event counts to 1-200.
- Since the `isDemo` column was added after some demo listings already existed in this project's dev database, they were backfilled once via `UPDATE "Listing" l SET "isDemo" = true FROM "User" u WHERE l."createdById" = u.id AND u.email LIKE '%@ligem-demo.invalid' AND l."isDemo" = false;` — not needed going forward since the generator sets the flag itself.

### Bulk actions (`/admin/projekte`, `/admin/termine`, `/admin/nutzer`)

Demo listings/events/users show a small amber "Demo" badge next to their name (`listing.isDemo`; for events via `event.listing?.isDemo` since `Event` has no `isDemo` column of its own; for users via the `@ligem-demo.invalid` email domain check, `DEMO_EMAIL_DOMAIN` from `src/lib/demo-data/shared.ts`). Each row has a checkbox (`name="listingIds"`/`"eventIds"`/`"userIds"`, `data-demo="true"` when applicable); a "Nur generierte auswählen" link (plus "Alle auswählen"/"Auswahl aufheben") toggles them via plain DOM queries in `src/components/bulk-select-controls.tsx`, a client component shared by all three pages — it selects purely by `form="<formId>"`, skipping `disabled` checkboxes, which is what lets it work across three different checkbox `name`s without modification. These checkboxes are **not** nested inside a `<form>` that wraps the list — each row already has its own single-item form(s) (`Freigeben`/`Ablehnen`/`Archivieren` on the first two pages, the roles-checkbox `Speichern` form on `/admin/nutzer`), and a literal nested `<form>` would be invalid HTML (the browser silently breaks it). Instead there's one outer bulk `<form id="bulk-projekte-form">`/`"bulk-termine-form"`/`"bulk-nutzer-form"` rendered once above the list, and every checkbox/bulk-button references it via the HTML `form="..."` attribute, which associates a control with a form anywhere in the document regardless of DOM nesting. The bulk buttons are plain submit buttons with different `formAction`s pointing at the respective `bulkReject*`/`bulkArchive*`/`bulkDelete*`/`bulkAddRole`/`bulkRemoveRole` functions in each route's `actions.ts` — a single `<form>` can route to different server actions per submit button this way. Bulk delete (unlike reject/archive/role changes, which are reversible) is a hard `deleteMany` and goes through `ConfirmSubmitButton`.

`/admin/termine` mirrors `/admin/projekte`'s structure exactly (same status tabs, same bulk-form pattern, same components) but defaults to the "Veröffentlicht" tab rather than "Wird geprüft" — Events are created as `PUBLISHED` directly with no moderation gate (see Pages above), so "Wird geprüft" is normally empty; this page exists purely to let admins reject/archive/delete events *after* the fact. `Event` has no `moderationNote`/`moderatedById` columns (unlike `Listing`), so its reject action has no note field.

`/admin/nutzer`'s bulk row has a role `<select>` plus "Rolle hinzufügen"/"Rolle entfernen" buttons (`bulkAddRole`/`bulkRemoveRole` — additive/subtractive on one role at a time across the selection, unlike the per-user form below it which replaces that one user's whole role set) alongside "Ausgewählte löschen" (`bulkDeleteUsers`). Two safety details specific to acting on user accounts:
- **You can never bulk-act on your own account**: the checkbox for the signed-in admin's own row is rendered `disabled` (so it's excluded from form submission regardless of any JS toggling — `BulkSelectControls` also skips `disabled` checkboxes so "Alle auswählen" doesn't even visually check it), and every bulk action additionally filters the acting admin's own id out of the submitted ids server-side (`selectedIds(formData, session.user.id)` in `actions.ts`) as defense in depth.
- **`bulkDeleteUsers` does not cascade a user's real content away.** `Listing.createdById`/`Event.createdById` are `ON DELETE RESTRICT` (see Demo data generators below) — deleting a user who still owns Listings/Events throws, which is caught and turned into the friendly `?error=besitzt-inhalte` message rather than silently wiping their projects/events as a side effect of an account deletion, or crashing the request. Users with no owned content delete cleanly.

## `/projekte` and `/termine` master-detail (inline preview panes)

Clicking a result on `/projekte` or `/termine` loads that listing's/event's detail **inline in the same right-hand results column** instead of navigating to the standalone `/projekte/[id]`/`/termine/[eventId]` page — the filter sidebar (and its map/calendar) stays mounted and untouched. This is a query-param mechanism, not a Next.js parallel/intercepting route: each `page.tsx` reads a `?projekt=<id>`/`?termin=<id>` search param and, when present and the item is visible to the viewer (`PUBLISHED`, or for listings also owner/ADMIN via the same `canManage` check as the standalone page), fetches and renders it via `<ListingDetail>`/`<EventDetail>` instead of the results `<ul>`; an invalid/inaccessible id is silently treated as "no selection" (falls back to the list) rather than erroring the whole page. `buildProjekteHref`/`buildTermineHref` (`(params, overrides) => string`, one per page.tsx) build a `/projekte?...`/`/termine?...` URL from the *current* search params with `overrides` applied (a value of `undefined` removes that key) — every result card/map-marker link uses it with `{ projekt: id }`/`{ termin: id }` so the rest of the active filters/map position survive the "navigation" (it's a normal same-route Link, not JS state), and each detail component's "← Zurück zur Liste" link uses it with that key set to `undefined`. Both href-builders also explicitly clear the page's transient flash param (`kontakt`/`angemeldet`) whenever selecting a *different* item or going back to the list — otherwise a stale "message sent" success banner would carry over and show again for an item whose form was never actually just submitted.

`src/components/listing-detail.tsx` (`ListingDetail`) / `src/components/event-detail.tsx` (`EventDetail`) hold the actual detail content (status banner, photo grid, description fields, attributes, contact/registration form, ...) — each is shared between its standalone page and its inline pane, parameterized by `returnTo` (where the contact/registration form's server action redirects back to after submitting — the standalone page passes its own fixed path, the inline pane passes the full current `/projekte?...`/`/termine?...` URL including the selection param) and an optional `backHref` (only set for the inline pane). `submitContactRequest` (`projekte/[id]/actions.ts`) and `submitEventRegistration` (`termine/actions.ts`) both read `returnTo` from a hidden form field and validate it's a same-origin path under their own route (`sanitizeReturnTo`, one per file) before redirecting there, since it's client-supplied.

**Cross-links between a listing's and an event's detail view always point at the inline `?projekt=`/`?termin=` pane, never at the other one's standalone page.** `EventDetail`'s "Veranstaltet von {Projektname}" link goes to `/projekte?projekt=<id>` (not `/projekte/<id>`), `ListingDetail`'s "Termine" list links go to `/termine?termin=<id>` each (not `/termine/<id>`), and `/projekte/page.tsx`'s map-popup "Nächste Termine" mini-list does the same — landing on either standalone page instead would silently drop that page's entire filter sidebar (search form, map/calendar), which is a real, previously-reported bug class rather than a stylistic preference.

### Selected-item marker on the map

`location-radius-picker.tsx` accepts an optional `selectedId` prop (matching a `resultItems` entry's `id`) — both page.tsx's pass the current `?projekt=`/`?termin=` value straight through (via `ProjekteSearchForm`/`TermineSearchForm`). When set, the matching item is rendered with its own distinct, larger pin (`createSelectedPinIcon` — secondary/green `SELECTED_PIN_SVG`, visually distinct from both the small primary-colored result dots and the primary-colored "search from" origin pin) added **directly to the map**, not into the `markerClusterGroup` — so it's never hidden inside a cluster bubble regardless of zoom level, and stays correct even while a detail is open, since it's rebuilt by the same `[resultItems, selectedId]` effect described above (see `renderResultsLayer`) whenever either changes.

Selecting an item also zooms the map to a ~20km view centered on it (`renderSelectedMarker`'s `focusCircle`/`fitBounds` in `location-radius-picker.tsx`), computed via a throwaway `L.circle({ radius: 20_000 })`'s bounds rather than a fixed zoom level, since the zoom that shows "20km on screen" varies with latitude and viewport size. **That circle must be added to the map before calling `.getBounds()`** — Leaflet's `Circle.getBounds()` reads back the circle's own projected screen position (`this._map`/`this._point`), which are only set once it's actually on the map — so it's added, `.getBounds()` is read, and it's removed again immediately (never visibly rendered, just used for that one computation). Deselecting (going back to the list) zooms back out to the overview — the bounds fitting every result + the search origin, captured once at mount into `overviewBoundsRef` — rather than leaving the map stuck on the last-viewed item.

### Prev/next navigation within the inline detail pane

Both `ListingDetail`/`EventDetail` accept optional `prevItem`/`nextItem` props (`{ href: string; label: string } | null`), rendered as a `‹`/`›` (`lucide-react` `ChevronLeft`/`ChevronRight`) link pair with the adjacent item's name, directly under the "← Zurück zur Liste" link and above the rest of the detail content. Each page.tsx computes these from the same ordered array it already renders as the results list — `/projekte/page.tsx` uses `sortedListings` (so prev/next follows whatever `sortierung` is active — Neueste/Entfernung/Name/Kosten), `/termine/page.tsx` uses `events` (chronological) — via `selectedIndex = <array>.findIndex((x) => x.id === selectedId)`, then `<array>[selectedIndex - 1]`/`[selectedIndex + 1]` (`null` at either end of the array, or when there's no selection at all). The hrefs are built the same way every other result link is (`buildProjekteHref`/`buildTermineHref` with the target id, clearing the transient flash param), so stepping prev/next preserves the active filters/map position exactly like clicking a result from the list does.

## Results summary above `/projekte` and `/termine`'s result lists

Both `/projekte/page.tsx` and `/termine/page.tsx` build a one-line summary above their results (`resultsSummary`, e.g. `"12 Termine gefunden für Art „Workshop", Zielgruppe „Familien mit Kindern""`) from whichever filters are actually active — resolved to their human-readable option names/labels, not raw ids/params — so the count has visible context for how it was produced. Only present filters are listed; `/termine`'s default "upcoming only" Zeitraum (no explicit `von`) isn't treated as an active filter. `/projekte`'s version additionally walks every active `advancedGroups` entry (not just Projekt Typ/Kategorie), since listings can have several attribute-group filters active at once, each rendered as its own `"{Gruppenname} „{Optionen}""` segment. This summary/list is only shown when no `?projekt=<id>`/`?termin=<id>` detail is open (see master-detail above).

`location-radius-picker.tsx`'s `RADIUS_STEPS` (used by both `/projekte` and `/termine`) go up to `[1, 5, 10, 20, 50, 75, 100, 150, 200, 300, null]` (`null` = "Alle").

Each result card's thumbnail (`/projekte/page.tsx` and `/termine/page.tsx`) is flush against the card's top/left/bottom edges rather than sitting as a small square inside the card's own padding: the outer `<Link>` drops its own padding (`overflow-hidden rounded-2xl`, no `p-*`) and instead wraps the text content in an inner `flex-1 p-4 sm:p-6` div, while the `<img>` itself is `aspect-[4/3] w-52 sm:w-60 shrink-0 self-start rounded-l-2xl object-cover` — rounded only on the left (matching the card's own corners) since its right edge is an interior boundary against the text, not a card corner. The image is sized by a **fixed width with the height derived from `aspect-[4/3]`**, not the reverse (a stretched `h-full` with width derived from an aspect-ratio) — the latter was tried first and is a trap: a flex/grid item whose cross-size comes from `align-items: stretch` (matching the card's own content-driven height) while its main-size is simultaneously meant to come from `aspect-ratio` creates a circular sizing dependency that at least Chromium resolves by inflating the row's own height far beyond what the text content needs, which then inflates the image further — not just a proportion mismatch but a runaway feedback loop. Fixing the width and letting only the height be `auto` (derived from the aspect ratio) has no such loop and is exact every time; the `self-start` keeps the now-shorter-than-the-card image anchored to the top-left instead of being stretched by the row's default `align-items: stretch`. The tradeoff is that unusually tall cards (e.g. several wrapped attribute badges) leave a sliver of plain card background below the image instead of the image reaching the bottom edge — acceptable since the aspect ratio (not full-height coverage) is the actual requirement.

## Reorderable photo galleries (`/projekte/[id]/bearbeiten`, event edit)

`src/components/reorderable-photo-gallery.tsx` (`ReorderablePhotoGallery`, client component) replaces the former static photo grid in both edit forms' "Fotos" sections. Tiles are reorderable two ways: native HTML5 `draggable` (desktop mouse) and ←/→ buttons (touch/keyboard, since HTML5 drag-and-drop barely works on touchscreens) — both call the same `reorderAction(orderedIds)` prop, a Server Action **called directly from client code** (not through a `<form>`) and parameterized via `.bind(null, listingId)`/`.bind(null, eventId)` at the call site (`reorderListingMedia`/`reorderEventMedia` in `media-actions.ts`/`event-media-actions.ts`) — `.bind()` on a Server Action produces another valid Server Action reference, which is how a Client Component can receive one pre-parameterized without a server component passing a plain (non-serializable) closure. Both reorder actions re-verify ownership, then reject the whole payload unless it's exactly a permutation of the existing media ids (no partial/tampered application) before persisting new `position` values in a `$transaction`. Position 0 is always the thumbnail shown on `/projekte`/`/termine`, hence the "Vorschau" badge on the first tile and the hint text above the grid.

## Deployment

See `DEPLOYMENT.md` for server installation (Docker Compose in production mode, migrations, reverse proxy/TLS, backups) and `scripts/deploy.sh`/`scripts/github-init.sh` for the corresponding automation — both scripts are written but intentionally never executed by Claude, since they push to a real GitHub remote / deploy to a real server. `prisma/seed.ts` skips creating its fixed-password local dev admin when `NODE_ENV=production`.

## Commands

Run everything via Docker (starts Postgres/Valkey/Meilisearch/MinIO and the Next.js dev server together):
```bash
docker compose up
```
The app is then served at http://localhost:3000, with dependent services bound to 127.0.0.1 on their default ports (Postgres 5432, Valkey 6379, Meilisearch 7700, MinIO 9000/9001).

Run app/package commands inside the running container (see the host-vs-container note above):
```bash
docker compose exec web sh -c "cd /workspace/apps/web && <command>"
```
Common commands:
```bash
pnpm dev             # dev server on 0.0.0.0:3000 (already running via docker compose up)
pnpm build           # production build
pnpm lint            # eslint
pnpm exec tsc --noEmit   # type-check only

pnpm db:migrate      # prisma migrate dev — create/apply a migration from schema changes
pnpm db:seed         # prisma db seed — runs prisma/seed.ts (categories, attribute groups, and — outside NODE_ENV=production — a dev admin login)
pnpm db:studio       # prisma studio — browse the dev database
pnpm exec prisma generate   # regenerate the client into src/generated/prisma (also runs on postinstall)
```
Note: `apps/web/.env` holds a host-reachable `DATABASE_URL` (`localhost:5432`) for any tooling invoked from outside Docker; inside the `web` container, `docker-compose.yml`'s `environment:` block (hostname `postgres`) takes precedence over `.env` — both point at the same `c1u3`/`c1db3` database.

There is no test setup yet.
